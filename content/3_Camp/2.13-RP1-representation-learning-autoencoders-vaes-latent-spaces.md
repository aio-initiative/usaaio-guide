## Autoencoder

### The problem

To generate images, a model first needs a compact description of what makes an image look real.

An image has far more numbers than it has things that vary. A 64 × 64 color photo of a face has 64 × 64 × 3 = 12,288 numbers, but between one face and another only a few things change: pose, lighting, expression, hair.

The running example shows the same thing at small scale. Its images have 4 pixels, and the two training images are LEFT, (1, 0, 1, 0), and RIGHT, (0, 1, 0, 1). Plotting just the first two pixels, both images and every blend of them lie on one line. A single number, how far along the line, is enough to say which image it is.

<Figure src="assets/module-media/generative-problem-autoencoder.svg" alt="A plot of the top-right pixel against the top-left pixel. LEFT is the point (1, 0) and RIGHT is the point (0, 1), joined by a heavy line labeled every blend of LEFT and RIGHT. Scattered gray dots, labeled other pairs of pixel values, fill the rest of the square.">
The first two pixels of the running example's images. The images lie on a line, so one number is enough to describe them.
</Figure>

Nobody tells the model which way the line runs. It has to find a short description like this on its own, from unlabeled images.

### Earlier approaches

#### Storing the images

Keeping the training set and returning a random image from it produces perfectly realistic images, but never a new one.

#### Principal component analysis

PCA finds the directions in which the images vary most and describes each image by a few numbers along those directions. It is fast and exact, but it can only describe data lying near a flat surface. Images of faces do not, so a few PCA numbers give blurry, ghostly faces.

### Encoder and decoder

**Two networks.** An **autoencoder** is two networks trained together. The **encoder** compresses an image into a short list of numbers, its **code**. The **decoder** turns the code back into an image.

<Figure src="assets/module-media/generative-autoencoder.svg" alt="The 4-pixel image LEFT, with pixels 1, 0, 1, 0, goes into an encoder, which outputs a code of one number, z = 1. A decoder turns the code back into an image with pixels 1, 0, 1, 0, the reconstruction. A note says: training makes the reconstruction match the input.">
The running example's autoencoder. Four numbers are squeezed into one and then rebuilt.
</Figure>

**The loss.** Training makes the output match the input, using the **mean squared error** between them: the average of the squared differences, pixel by pixel.

$$
\text{loss} = \frac{1}{n} \sum_{i=1}^{n} (\text{output}_i - \text{input}_i)^2
$$

For example, an input of (0.9, 0.1, 1, 0) and an output of (0.95, 0.05, 0.95, 0.05) differ by 0.05 in every pixel, so the loss is $0.05^2 = 0.0025$. No labels are needed, because the input is its own target.

Binary cross-entropy is often used as a surrogate for scaled pixel values. Changing MSE to BCE alone does not guarantee sharper images.

**Why the code is short.** The code is too short to hold every pixel, so the encoder must keep only what matters most. A code of 1 number for a 4-pixel image has to drop three-quarters of the numbers. With nonlinear layers, an autoencoder can describe curved surfaces that PCA cannot.

**Linear autoencoders and PCA.** With a linear encoder, an affine decoder (a linear map plus a constant) and the squared error as the loss, the best code describes the same line, or flat surface, that PCA finds. This chapter's autoencoder is built that way. PCA of LEFT and RIGHT finds the mean image (0.5, 0.5, 0.5, 0.5) and the direction (0.5, −0.5, 0.5, −0.5), and an image's position along that direction, (image − mean) · direction, is its code: 1 for LEFT and −1 for RIGHT. The decoder's output, mean + z × direction, is the reconstruction rule of the running example below.

**Denoising autoencoders.** Noise is added to each training image before it goes in, and the output is compared with the clean image. Copying the input then scores worse than removing the noise, so the network has to learn what clean images look like, even with a code as long as the image. For noisy LEFT, (0.9, 0.1, 1, 0), copying it scores $(0.1^2 + 0.1^2 + 0^2 + 0^2) \div 4 = 0.005$ against LEFT. This chapter's autoencoder returns (0.95, 0.05, 0.95, 0.05), the nearest point on its line, and scores $0.05^2 = 0.0025$. [Removing noise](3.16-GM4-generative-adding-noise.md#lesson-removing-noise), in part 4, trains diffusion on noisy images in the same way.

<Figure src="assets/module-media/generative-projection.svg" alt="A plot of the bottom-left pixel against the top-left pixel. A diagonal line, labeled every output of the decoder, passes through RIGHT at (0, 0) with code -1, the mean image at (0.5, 0.5) with code 0, and LEFT at (1, 1) with code 1. Noisy LEFT, an open dot at (0.9, 1), sits just off the line, and a short dashed segment joins it to a filled dot on the line at (0.95, 0.95), labeled rebuilt, code 0.9.">
Two of the four pixels. Every output of the decoder lies on the line, and encoding then decoding moves noisy LEFT to the nearest point on it.
</Figure>

**Sparse autoencoders.** A **sparse autoencoder** asks that only a small portion of its units be active for a given input. One option is an activation penalty such as $\lambda\|z\|_1$.

A **contractive autoencoder** penalizes the encoder's sensitivity to its input: if $J$ is the Jacobian of the encoder, its loss is the reconstruction loss plus $\lambda\mathbb{E}_x\|J(x)\|_F^2$. For a small perturbation $\delta$, the code changes approximately by $J(x)\delta$. Reducing the Jacobian discourages large code changes from small input changes. Reconstruction pushes back, since a completely constant code cannot reconstruct varied inputs.

**Uses.** Autoencoders are used for compression and for removing noise. An image unlike anything in training does not lie on the line the decoder's outputs lie on, so its reconstruction error is high, and that error is used as an anomaly score. The autoencoder inside Stable Diffusion appears again in [Guidance and Stable Diffusion](3.16-GM4-generative-adding-noise.md#lesson-guidance-and-stable-diffusion).

### Running example

#### The images

Images in this chapter have 4 pixels, in a 2 × 2 grid. The training set holds two images:

| Image | Top-left | Top-right | Bottom-left | Bottom-right |
|---|---|---|---|---|
| LEFT | 1 | 0 | 1 | 0 |
| RIGHT | 0 | 1 | 0 | 1 |

#### Encoder and decoder

The autoencoder squeezes each image into a single number. The encoder adds the left column and subtracts the right column, then halves: z = (top-left − top-right + bottom-left − bottom-right) ÷ 2. The decoder sets each left pixel to 0.5 + z ÷ 2 and each right pixel to 0.5 − z ÷ 2.

| Input | Code z | Reconstruction |
|---|---|---|
| LEFT (1, 0, 1, 0) | 1 | (1, 0, 1, 0) |
| RIGHT (0, 1, 0, 1) | −1 | (0, 1, 0, 1) |
| Noisy LEFT (0.9, 0.1, 1, 0) | 0.9 | (0.95, 0.05, 0.95, 0.05) |

Both training images come back exactly, so no training could do better. The noisy image comes back cleaner: its rows now match, because the code has no room to describe the noise.

#### Generating

To generate a new image, pick a code and decode it. But the only codes seen in training are 1 and −1, and nothing says what other codes mean. The code 0 gives (0.5, 0.5, 0.5, 0.5), a gray square that looks like neither image, and the code 3 gives (2, −1, 2, −1), which is not even a valid image. A real autoencoder scatters its codes irregularly, so most random codes decode to nonsense.

```python
import numpy as np

pattern = np.array([1.0, -1.0, 1.0, -1.0])
encode = lambda x: x @ pattern / 2
decode = lambda z: 0.5 + z * pattern / 2

for x in ([1, 0, 1, 0], [0, 1, 0, 1], [0.9, 0.1, 1, 0]):
    z = encode(np.array(x, dtype=float))
    print(z, decode(z))
print(decode(0.0), decode(3.0))    # gray, and not a valid image
```

### Common questions

**Why not make the code as long as the image?** Then the encoder could copy every pixel into the code and the decoder could copy them back, with a loss of 0 and nothing learned. The short code is what forces the network to find what the images have in common.

**Why does the noisy image come back cleaner?** The code is one number, 0.9, so the decoder can only produce images of the form it knows: left pixels alike, right pixels alike. The unevenness between the two rows has no place in the code and is dropped.

**Is training supervised?** It needs no labels. The target for each image is the image itself, so any collection of images will do.

**Does a low reconstruction loss mean the code is useful?** Not for every purpose. Pixel error may reward accurately reproducing a large background even when a small symbol determines the class. A classifier trained on the code tests whether that symbol's identity is still accessible, and it can disagree with the reconstruction error without either measurement being wrong.

**Can an autoencoder generate new images?** Not reliably. Only the codes seen in training, 1 and −1 here, are sure to decode well. Code 0 gives a gray square and code 3 gives pixels outside the valid range. The [VAE](#lesson-vae), next, fixes this.

**Why don't my encoder's weights match PCA's components?** The reconstruction does not fix the code's units. Multiply every code by 10 and divide the decoder's weights by 10 and every rebuilt image is unchanged. With several code numbers, multiplying the encoder by any invertible matrix and the decoder by its inverse changes nothing either. So a linear autoencoder can rebuild exactly the line PCA finds and still carry different weights. Compare what the two reconstruct, not their weights.

The next section, [VAE](#lesson-vae), arranges the codes so that random ones make sense.

## VAE

### The problem

The autoencoder above can rebuild an image from its code. To generate a new image, one would pick a code and decode it. The trouble is knowing which codes to pick.

For example, that autoencoder uses the code 1 for LEFT and −1 for RIGHT, and nothing else. No other code was ever seen in training. The code 0 decodes to a gray square, and the code 3 to pixels of 2 and −1, which is not an image at all.

<Figure src="assets/module-media/generative-problem-vae.svg" alt="A number line of codes. The codes -1 and 1, drawn as filled dots, were used in training and decode to RIGHT and LEFT. The codes 0 and 3, drawn as empty dots, were not: 0 decodes to a gray image with every pixel 0.5, and 3 decodes to pixels of 2 and -1, labeled not an image.">
What four codes decode to. Only the two used in training give an image.
</Figure>

With real images it is worse. The codes have many numbers, and training scatters them with no agreed layout, so a code chosen at random almost always lands in a gap and decodes to nonsense.

To generate, the codes need to fill a known region with no gaps, so that any code drawn from that region decodes to a realistic image.

### Earlier approaches

#### Plain autoencoders

As with the plain autoencoder above, the codes land wherever training puts them. Picking a code near a training image's code gives a near-copy of that image. Picking one elsewhere gives nonsense.

#### Boltzmann machines

Earlier generative networks, such as the deep belief networks of Hinton et al. (2006), could produce new images, but drawing each one needed a long chain of random updates, and they were slow to train.

### Codes as ranges

A **variational autoencoder** (VAE) makes two changes to the autoencoder.

**A range for each code.** The encoder outputs a **range** for each code: a mean $\mu$ and a spread $\sigma$. The code is drawn at random from that range,

$$
z = \mu + \sigma \times (\text{a random number from a standard normal distribution}),
$$

so nearby codes must all decode to similar images. For example, with $\mu = 1$ and $\sigma = 0.5$, a random number of −0.4 gives $z = 1 + 0.5 \times (-0.4) = 0.8$.

**Gradients through the draw.** Training needs the slope of the loss with respect to $\mu$ and $\sigma$, and a random draw has none. Writing the draw as $z = \mu + \sigma\varepsilon$, with $\varepsilon$ the random number, moves the randomness into $\varepsilon$, which has no weights, so $dz/d\mu = 1$ and $dz/d\sigma = \varepsilon$. This is the **reparameterization trick**. In the example, $z = 0.8$ decodes to (0.9, 0.1, 0.9, 0.1), a squared error against LEFT of $4 \times 0.1^2 = 0.04$. Here the error is $(1 - z)^2$, with slope $-2(1 - z) = -0.4$, so by the chain rule the slopes are $-0.4 \times 1 = -0.4$ for $\mu$ and $-0.4 \times (-0.4) = 0.16$ for $\sigma$. A detached sample loses the reconstruction gradient into the encoder. A gradient step raises $\mu$ and narrows $\sigma$. The KL term below pulls the other way: its slope is 1 for $\mu$ and $\sigma - 1/\sigma = -1.5$ for $\sigma$. Encoders usually output $\ln \sigma^2$ rather than $\sigma$, so that any number is a valid output: $\ln \sigma^2 = -1.386$ gives $\sigma = 0.5$.

<Figure src="assets/module-media/generative-reparameterization.svg" alt="Three boxes on the left: mu = 1 and sigma = 0.5, labeled from the encoder, and a dashed box epsilon = -0.4, labeled random, no weights. Arrows from all three lead to a heavy box z = mu + sigma epsilon = 0.8. Above it: slopes dz/dmu = 1 and dz/dsigma = epsilon = -0.4. The code goes into a decoder, which outputs the 2 by 2 image 0.9, 0.1, 0.9, 0.1, with error 0.04 against LEFT.">
The draw written as $z = \mu + \sigma\varepsilon$. The random number sits outside the path from the encoder to the loss, so both of the encoder's outputs get a slope.
</Figure>

**A second loss term.** The loss adds the **KL divergence**, which measures how far each range is from a standard one with mean 0 and spread 1:

$$
\text{KL} = \tfrac{1}{2}\left(\sigma^2 + \mu^2 - 1 - \ln \sigma^2\right)
$$

It is 0 only when $\mu = 0$ and $\sigma = 1$. For example, $\mu = 1$ and $\sigma = 1$ give $\tfrac{1}{2}(1 + 1 - 1 - 0) = 0.5$. No sampling is needed to evaluate this term. Sampling is needed for the reconstruction expectation, which averages over codes drawn from the encoder's range.

<Figure src="assets/module-media/generative-vae.svg" alt="Two plots over the code z. On the left, the autoencoder: one vertical line at -1 for RIGHT and one at 1 for LEFT, with the space between labeled nothing here. On the right, the VAE: two bell curves, for RIGHT and LEFT, centered either side of 0 and overlapping in the middle, with a dashed bell curve centered at 0 for the standard range.">
A sketch. The autoencoder gives each image one code and leaves gaps. The VAE gives each image a range, and the ranges fill the space around 0.
</Figure>

**What the KL term does.** It pulls every image's range toward the center and keeps it wide, so the ranges overlap and fill the space around 0 without gaps. To generate, draw $z$ from the standard range and decode it.

**The cost.** The cost is blur. Where the ranges of two different images overlap, the decoder cannot tell which one the code came from, and the mean squared error is lowest for an average of the two.

#### The bound

**The model.** A VAE is a probability model of images. A code $z$ is drawn from the standard range, and the decoder gives each pixel a normal spread around its output. Generating from this model draws the code and then the pixel noise. Decoding a code and returning the output alone drops that noise, giving a narrower, less variable distribution than the model itself. Before comparing sharpness or diversity, say which of the two was made. With a variance of 0.5, a spread of $\sqrt{0.5} = 0.707$,

$$
\ln p(x \mid z) = -2.2895 - (\text{squared error between } x \text{ and the decoder's output}),
$$

since $-2\ln(2\pi \times 0.5) = -2.2895$ and $1 \div (2 \times 0.5) = 1$. Training should make the training images likely, that is, raise $\ln p(x)$, where $p(x)$ averages $p(x \mid z)$ over every code. The **posterior** $p(z \mid x)$ says which codes could have produced $x$. For a real decoder neither has a formula. The running example's decoder is linear, so both do: $\ln p(\text{LEFT}) = -3.1721$, and LEFT's posterior is the range with $\mu = 0.667$ and $\sigma = 0.577$.

**The bound.** The encoder's range $q(z \mid x)$ stands in for the posterior. Writing $p(x) = p(x, z) \div p(z \mid x)$, averaging over codes drawn from $q$, and multiplying inside the logarithm by $q \div q$ splits $\ln p(x)$ in two:

$$
\ln p(x) = \mathbb{E}_{q}\Big[\ln \frac{p(x, z)}{q(z \mid x)}\Big] + \mathbb{E}_{q}\Big[\ln \frac{q(z \mid x)}{p(z \mid x)}\Big].
$$

The second average is the KL divergence from $q$ to the posterior, which is never negative. Dropping it leaves the **evidence lower bound** (ELBO), and splitting $p(x, z) = p(x \mid z)\, p(z)$ gives its two terms:

$$
\text{ELBO} = \mathbb{E}_{q}\big[\ln p(x \mid z)\big] - \text{KL}\big(q \,\|\, \mathcal{N}(0, 1)\big) \le \ln p(x).
$$

**The two terms.** The first rewards codes that decode back to $x$, and with a normal spread it is a constant minus a multiple of the squared error. The second is this page's KL term. With a variance of 0.5 the multiple is 1, so the ELBO is $-2.2895$ minus this page's loss, the squared error summed over the pixels plus the KL. For LEFT with $\mu = 1$ and $\sigma = 0.5$, codes from the range decode to points along the autoencoder's line, which moves 1 unit for each unit of $z$, so the average squared error is the error at $\mu$, here 0, plus $\sigma^2 = 0.25$. The first term is $-2.2895 - 0.25 = -2.5395$, and the ELBO is $-2.5395 - 0.8181 = -3.3576$.

**The gap.** The ELBO falls short of $\ln p(x)$ by the KL from the encoder's range to the posterior, so it is exact only when the range is the posterior itself:

| LEFT's range | First term | KL term | ELBO | Gap to −3.1721 |
|---|---|---|---|---|
| μ = 1, σ = 0.5 | −2.5395 | 0.8181 | −3.3576 | 0.1855 |
| μ = 0.667, σ = 0.577, the posterior | −2.7339 | 0.4382 | −3.1721 | 0 |
| μ = 0, σ = 1, the standard range | −4.2895 | 0 | −4.2895 | 1.1174 |

Raising the ELBO raises $\ln p(x)$ and moves the encoder's range toward the posterior, where this page's loss is lowest: wider than $\sigma = 0.5$ and closer to 0 than $\mu = 1$. The posterior's $\mu$ is exactly $2/3$ and its $\sigma^2$ is $1/3$, so its average squared error is $(1 - 2/3)^2 + 1/3 = 0.4444$ and its first term is $-2.2895 - 0.4444 = -2.7339$. The standard range costs no KL, but its codes decode far from LEFT, so its bound is the lowest of the three.

#### Conditional VAEs

**Conditioning on a label.** Giving a label $y$ to both the encoder and the decoder, usually as an extra input, lets a VAE make what is asked for. The bound is the same with every term conditioned on $y$. To generate, choose $y$, draw $z$ from the standard range, and decode both. In the running example, a label that names LEFT or RIGHT leaves the code nothing to describe: each image can keep the standard range, a KL of 0, and still decode to itself. Without the label, LEFT's best range, the posterior above, costs a KL of 0.438. With real images, the code keeps what the label does not say, such as how a digit is written.

### Running example

#### The KL term

Suppose the encoder gives LEFT a mean of 1. The KL term for some possible ranges:

| μ | σ | KL |
|---|---|---|
| 1 | 0.5 | 0.818 |
| 1 | 1 | 0.5 |
| 0.5 | 1 | 0.125 |
| 0 | 1 | 0 |

A narrow range far from 0 costs the most, so training widens LEFT's range and moves it toward 0, and does the same for RIGHT from the other side. With the autoencoder's decoder, codes drawn from the standard range decode to:

| Code z | Image |
|---|---|
| 0.8 | (0.9, 0.1, 0.9, 0.1), mostly LEFT |
| −0.3 | (0.35, 0.65, 0.35, 0.65), leaning RIGHT |
| 0 | (0.5, 0.5, 0.5, 0.5), a gray blend of both |

#### Blur

Codes between the two training codes decode to blends of LEFT and RIGHT, and the closer a code is to 0, where the two ranges overlap most, the grayer the image. A real VAE's decoder is trained on codes drawn from these ranges, so it learns to decode every likely code sensibly, but the gray blends are the blur described above.

```python
import numpy as np

kl = lambda mu, s: 0.5 * (s ** 2 + mu ** 2 - 1 - np.log(s ** 2))
for mu, s in [(1, 0.5), (1, 1), (0.5, 1), (0, 1)]:
    print(mu, s, round(kl(mu, s), 3))

pattern = np.array([1.0, -1.0, 1.0, -1.0])
for z in (0.8, -0.3, 0.0):
    print(z, 0.5 + z * pattern / 2)
```

### Common questions

**Why a mean of 0 and a spread of 1?** That range, the standard normal distribution, is easy to draw from. If all the codes fill it, generating is simple: draw a number from it and decode.

**Why not let the KL term win completely?** If every image had exactly $\mu = 0$ and $\sigma = 1$, the KL term would be 0, but every image would have the same range and the decoder could not tell them apart. The reconstruction loss pulls the ranges apart and the KL term pulls them together, and training settles in between. Inspect KL by coordinate across many inputs, variation in posterior means, and whether changing $z$ changes decoder predictions.

**Why draw the code at random during training?** So that the decoder sees a whole neighborhood of codes for each image and has to decode all of them well. That is what removes the gaps between the codes.

**How are the two loss terms balanced?** By a weight on the KL term. A larger weight fills the space better and blurs more. A smaller one gives sharper reconstructions and leaves gaps. KL annealing starts with a small KL weight so reconstruction can encourage use of the latent code early in training. A free-bits objective stops charging additional KL below a selected allowance.
