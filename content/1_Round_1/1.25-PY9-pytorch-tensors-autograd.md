## Overview

A tensor is PyTorch's array: a NumPy array plus a device it lives on and a flag that says whether autograd is recording it. A PyTorch problem on a USAAIO round hands you tensors and expects three things. Build and inspect them. Compute with them without Python loops, which Round 1 has banned outright in its vectorization problems. Recognize the handful of error messages that appear when shapes, dtypes or devices disagree. The second half of the module is autograd as it appears in code: `requires_grad`, `backward()` and `.grad`, with the rules that cause most of the bugs around them.

## Example: all pairwise distances, no loop

The first two parts of the problem below are two vectorization tasks, to be written with no Python loops and no comprehensions. The notebook inspects your functions, rejects any loop, and compares both answers with a slow loop-based reference.

- **k-nearest neighbors.** Compute all pairwise squared distances between the query points and the reference points without building an `(n, m, d)` tensor, take the `k` nearest with `topk`, and count the votes per class with `scatter_add_`. Ties go to the smallest label.
- **Padded sequences.** For a batch of sequences padded to one length, build the padding mask from the lengths, then compute each sequence's mean, its attention-pooled vector with a masked softmax, and its last real vector. The padding holds garbage, so any answer that reads it is visibly wrong.

<ProblemCard id="pt-tensor-drills" />

Take 1,000 points and 600 points, each a row of 8 numbers, and ask for the $1000 \times 600$ table $D$ with $D_{ij} = \lVert \mathbf{x}_i - \mathbf{y}_j \rVert^2$. The loop version is easy to write and the kind of thing a vectorization problem forbids:

```python
import torch

torch.manual_seed(0)
X = torch.randn(1000, 8)      # 1000 points in 8 dimensions
Y = torch.randn(600, 8)       # 600 points

def pairwise_loop(X, Y):
    D = torch.zeros(len(X), len(Y))
    for i in range(len(X)):
        for j in range(len(Y)):
            D[i, j] = ((X[i] - Y[j]) ** 2).sum()
    return D
```

600,000 tiny tensor operations, one per entry, take 4.5 seconds on a laptop. The same table takes three tensor operations and a few milliseconds, once the shapes are arranged so that broadcasting does the pairing. The implementation section returns to it after the tools are in place.

## Explanation

### Tensors, shapes, dtypes

Creation looks like NumPy:

```python
a = torch.tensor([[1., 2.], [3., 4.]])    # from data
z = torch.zeros(3, 5)                     # shape (3, 5)
r = torch.arange(12).reshape(3, 4)        # 0 to 11 in a 3 x 4 grid
g = torch.randn(2, 3)                     # standard normal draws

print(a.shape, a.dtype, a.device)
```

Shape, dtype and device, in that order:

```output
torch.Size([2, 2]) torch.float32 cpu
```

PyTorch's default float is float32. NumPy's is float64, so `torch.from_numpy(arr)` on a float array gives a float64 tensor, and feeding one into float32 weights fails with `RuntimeError: expected scalar type Float but found Double`. The fix is an explicit `.float()` at the boundary. The other dtype rule that comes up constantly: class indices for `nn.CrossEntropyLoss` go in a `torch.long` tensor. The loss also accepts a float target of class probabilities, so a float one-hot vector is allowed, but a float tensor holding an index is rejected.

**Random numbers.** `torch.randn` and every other random draw come from one generator, and `torch.manual_seed(0)` resets it. Call it before the first draw and a run repeats exactly, so the listings in this chapter start with it. The same generator shuffles a `DataLoader` and draws dropout masks, so one seed makes a whole training run repeatable on one machine.

### Views and copies

Slicing does not copy. `b = a[0]` and `b = a[:, 1:3]` return **views** that share memory with `a`, so writing through the view writes the original:

```python
a = torch.zeros(3, 3)
b = a[0]        # a view of the first row
b += 1          # in place
print(a)
```

The first row of `a` changed:

```output
tensor([[1., 1., 1.],
        [0., 0., 0.],
        [0., 0., 0.]])
```

`reshape`, `view`, `.T` and `permute` return views when they can. Sharing saves the copy, and it means a write in one place shows up in the other. When an independent tensor is needed, ask for one with `.clone()`. Methods ending in an underscore, `add_`, `mul_`, `fill_`, `zero_`, change the tensor in place instead of returning a new one.

Two indexing forms do copy: boolean masks (`a[a > 0]`) and integer-array indexing (`a[[0, 2]]`). Both are advanced indexing, which always makes a copy, even when the entries it picks happen to sit evenly spaced in memory. NumPy has the same rule.

<ProblemCard id="pta-copy-or-view" />

One rule is specific to PyTorch. `view` needs the entries stored in memory in the order the tensor reads them, which is called **contiguous**. `permute` and `.T` change the reading order without moving any data, so `x.T.view(-1)` raises `RuntimeError: view size is not compatible ...`. Call `.contiguous()` first, or use `reshape`, which copies only when it must.

NumPy arrays share memory the same way. `torch.from_numpy(arr)` and `t.numpy()` both return an object backed by the original's memory, so a write through one shows in the other. `.numpy()` needs a CPU tensor that is not being recorded, so the general form is `t.detach().cpu().numpy()`.

### Broadcasting

Broadcasting is how a loop becomes one expression. When two shapes meet:

1. Right-align the shapes. Missing leading dimensions count as size 1.
2. Two sizes are compatible if they are equal or one of them is 1.
3. Every size-1 dimension is stretched, without copying, to match the other.

<Figure src="assets/module-media/broadcasting.svg" alt="A column of three cells holding 1, 2, 3, plus a row of four cells holding 10, 20, 30, 40, equals a three by four grid whose entry in row i and column j is the sum of the two.">
A $(3, 1)$ column plus a $(1, 4)$ row is a $(3, 4)$ grid: the column is stretched across four columns and the row down three rows.
</Figure>

```python
u = torch.tensor([[1.], [2.], [3.]])      # (3, 1)
v = torch.tensor([10., 20., 30., 40.])    # (4,), read as (1, 4)
print((u + v).shape)
```

The shapes right-align as $(3, 1)$ and $(1, 4)$, so both size-1 dimensions stretch:

```output
torch.Size([3, 4])
```

`(3,) + (4,)` is an error, because 3 and 4 are neither equal nor 1: `RuntimeError: The size of tensor a (3) must match the size of tensor b (4) at non-singleton dimension 0`. A singleton dimension is one of size 1.

One idiom covers most pairwise work: insert a size-1 axis with `None` (or `unsqueeze`) so that the dimension you want paired up lines up with a 1 on the other side. `X[:, None, :]` turns a $(1000, 8)$ tensor into $(1000, 1, 8)$, and `Y[None, :, :]` turns $(600, 8)$ into $(1, 600, 8)$. Subtract them and the result is $(1000, 600, 8)$: every point of $X$ paired with every point of $Y$. Read broadcasting code by tracking the shape through each line.

### Reductions and matmul

A reduction collapses dimensions, and `dim=` names the one that disappears:

```python
s = torch.randn(32, 10)      # a batch of 32 score vectors
print(s.sum().shape, s.mean(dim=0).shape, s.argmax(dim=1).shape,
      s.sum(dim=1, keepdim=True).shape)
```

Everything, one number per class, one number per example, and one number per example with its axis kept:

```output
torch.Size([]) torch.Size([10]) torch.Size([32]) torch.Size([32, 1])
```

`keepdim=True` keeps the collapsed axis as size 1 so the result broadcasts back against the original. Row-normalizing a matrix is `s / s.sum(dim=1, keepdim=True)`, and without `keepdim` the shapes no longer line up.

`@` (`torch.matmul`) is matrix multiplication: matrix times matrix, or matrix times vector. With more than two axes it multiplies the last two and treats the rest as a batch, so `(B, N, K) @ (B, K, M)` gives `(B, N, M)`, one product per batch element. `*` is always elementwise. Shapes usually catch a mix-up, except when both matrices happen to be square.

### Operations that replace loops

Most loops a problem forbids are one of a dozen named operations:

| The loop you would write | The operation |
|---|---|
| An `if` on every element | `torch.where(condition, a, b)` |
| A running total | `cumsum` |
| The $k$ largest, or a sort | `topk`, `sort`, `argsort` |
| Joining tensors | `cat` along an existing axis, `stack` along a new one |
| A count or a sum per group | `bincount`, `scatter_add_` |
| One entry from each row | `gather`, or indexing with `torch.arange(N)` |
| A product over any pairing of axes | `einsum` |

Each line below is one of them:

```python
v = torch.tensor([3., -1., 4., -1., 5.])
print(torch.where(v > 0, v, torch.zeros_like(v)))      # choose elementwise by a condition
print(v.cumsum(dim=0))                                  # running sums
print(v.topk(2).indices, v.argsort())                   # the two largest, and the sorting permutation
print(torch.cat([v[:2], v[3:]]), torch.stack([v, v]).shape)   # join along an axis, or stack on a new one
labels = torch.tensor([0, 2, 2, 1, 2])
print(torch.bincount(labels), torch.zeros(3).scatter_add_(0, labels, v))   # a count and a sum per class
```

`scatter_add_` adds each entry of `v` into the slot named by its label, which is the per-group sum that otherwise takes a loop over the groups:

```output
tensor([3., 0., 4., 0., 5.])
tensor([ 3.,  2.,  6.,  5., 10.])
tensor([4, 2]) tensor([1, 3, 0, 2, 4])
tensor([ 3., -1., -1.,  5.]) torch.Size([2, 5])
tensor([1, 1, 3]) tensor([ 3., -1.,  8.])
```

Two more come up in every classifier. Picking one entry per row, such as the probability a model gives each example's true class, is `gather` or an integer-array index. A matrix product over any pairing of axes is `einsum`:

```python
torch.manual_seed(0)
probs = torch.softmax(torch.randn(4, 3), dim=1)
y = torch.tensor([0, 2, 1, 2])
print(probs.gather(1, y[:, None]).squeeze(1))           # each row's probability for its own label
print(probs[torch.arange(4), y])                        # the same, by integer-array indexing
print(torch.allclose(torch.einsum("ij,kj->ik", X, Y), X @ Y.T, atol=1e-5))
```

The subscripts in `einsum` name the axes of each input and of the output, and an axis missing from the output is summed over, so `"ij,kj->ik"` is $X Y^\top$:

```output
tensor([0.8446, 0.1051, 0.5382, 0.4961])
tensor([0.8446, 0.1051, 0.5382, 0.4961])
True
```

### Autograd in code

Set `requires_grad=True` on a tensor and PyTorch records every operation on it. Call `.backward()` on a scalar result and the gradient appears in `.grad`:

```python
x = torch.tensor([1., 2., 3.], requires_grad=True)
y = (x ** 2).sum()      # x1^2 + x2^2 + x3^2
y.backward()
print(x.grad)           # 2x
```

The derivative of $x_i^2$ is $2x_i$:

```output
tensor([2., 4., 6.])
```

Four mechanics, each a standing source of bugs:

- **Gradients accumulate.** A second `.backward()` adds to `.grad` instead of replacing it. Run `y = (x ** 2).sum()` and `y.backward()` again, and `x.grad` reads `tensor([4., 8., 12.])`. This is why every [training loop](1.26-PY10-training-loop-in-pytorch.md) calls `optimizer.zero_grad()`.
- **`.backward()` needs a scalar.** Loss functions end in a `mean()` or `sum()` for this reason. On a vector it raises `RuntimeError: grad can be implicitly created only for scalar outputs`.
- **Only leaves get `.grad`.** A tensor you created with `requires_grad=True` is a leaf. A result computed from one is not, and its `.grad` stays `None` unless you call `.retain_grad()` on it first.
- **Leaving the graph is explicit.** `with torch.no_grad():` runs a block without recording anything, for evaluation and manual weight updates. `.detach()` returns a view cut off from its history. `.item()` turns a one-element tensor into a Python number. Logging the loss as `losses.append(loss)` instead of `loss.item()` keeps the whole computation graph of every iteration alive, which is a memory leak.

<ProblemCard id="pta-logging-the-whole-graph" />

Autograd also checks derivations. For $f(\mathbf{x}) = \mathbf{x}^\top A \mathbf{x}$ the gradient is $(A + A^\top)\mathbf{x}$, and four lines check it:

```python
A = torch.randn(5, 5)
x = torch.randn(5, requires_grad=True)
(x @ A @ x).backward()
print(torch.allclose(x.grad, (A + A.T) @ x))
```

The derivation and autograd agree:

```output
True
```

Every derivation in [Backpropagation by Hand](2.1-MA4-backpropagation-mechanics.md) can be checked the same way, which catches a sign error before it costs the problem.

Autograd differentiates the operations you typed, not the function they compute. The norm $\lVert\mathbf{x}\rVert_2$ has gradient $\mathbf{x}/\lVert\mathbf{x}\rVert_2$ everywhere except the origin, where it has a kink. Written as `(x ** 2).sum().sqrt()`, the chain rule at $\mathbf{x} = \mathbf{0}$ multiplies $1/(2\sqrt{0}) = \infty$ by $2\mathbf{x} = \mathbf{0}$, and `.grad` comes back all `nan`. `torch.linalg.norm` treats the origin as a special case and returns $\mathbf{0}$. Same function, different gradients.

### Devices

`x.to('cuda')` moves a tensor to the GPU and `x.to('cpu')` brings it back. Models move the same way. Every tensor in an expression must live on the same device, or you get `RuntimeError: Expected all tensors to be on the same device`. The standard pattern:

```python
device = 'cuda' if torch.cuda.is_available() else 'cpu'
model = model.to(device)
xb, yb = xb.to(device), yb.to(device)
```

<Warning>

USAAIO Round 1 is CPU-only: GPUs are neither needed nor allowed. Round 2
provides L4 GPUs and some problems expect them. Write code that runs on
either device, as above, and you never have to think about which round you
are in.

</Warning>

## Implementation

Back to the pairwise distances. Insert the size-1 axes, let the subtraction broadcast, and sum out the last dimension:

```python
diff = X[:, None, :] - Y[None, :, :]      # (1000, 1, 8) - (1, 600, 8) -> (1000, 600, 8)
D = (diff ** 2).sum(dim=-1)               # (1000, 600)
print(D.shape)
print(torch.allclose(D, pairwise_loop(X, Y), atol=1e-4))
```

Same table as the loop, in milliseconds instead of 4.5 seconds:

```output
torch.Size([1000, 600])
True
```

The price is the intermediate `diff`, which holds $1000 \times 600 \times 8 = 4.8 \times 10^6$ numbers. For larger inputs that runs out of memory, and the fix is algebra, not a loop. Expanding the square,

$$
\lVert \mathbf{x} - \mathbf{y} \rVert^2 = \lVert \mathbf{x} \rVert^2 + \lVert \mathbf{y} \rVert^2 - 2\,\mathbf{x}^\top \mathbf{y},
$$

so the whole table is two row sums and one matrix product:

```python
D = (X ** 2).sum(dim=1, keepdim=True) + (Y ** 2).sum(dim=1) - 2 * X @ Y.T
```

The three terms have shapes $(1000, 1)$, $(600,)$ and $(1000, 600)$, and broadcasting lines them up. No $(1000, 600, 8)$ intermediate exists, and it is faster again. This is the version to write when either point set is large.

## Common errors

Almost every beginner PyTorch failure is one of six messages. Read them once and the cause is recognizable on sight:

1. `mat1 and mat2 shapes cannot be multiplied (32x784 and 28x128)`. An `nn.Linear(28, 128)` was fed a `(32, 784)` batch. Print shapes at each stage and find where they stop matching the plan.
2. `expected scalar type Float but found Double`. A float64 tensor, usually from NumPy, met float32 weights. Call `.float()` at the boundary.
3. `Expected all tensors to be on the same device`. The model is on the GPU and the batch on the CPU, or the reverse. Move both.
4. `a leaf Variable that requires grad is being used in an in-place operation`. This is `w += ...` on a parameter outside `no_grad()`. Manual updates belong inside `with torch.no_grad():`.
5. `grad can be implicitly created only for scalar outputs`. `.backward()` was called on a vector. Reduce it to one number first.
6. `Trying to backward through the graph a second time`. `.backward()` frees the graph after one use. Run the forward pass again before the next call.
