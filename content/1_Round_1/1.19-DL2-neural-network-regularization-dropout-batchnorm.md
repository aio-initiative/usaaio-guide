## Overview

An **affine layer** computes $W\mathbf{x} + \mathbf{b}$, a matrix product plus a bias. It is the syllabus's name for `nn.Linear`, the layer from [The Multilayer Perceptron](1.18-DL1-neural-networks-perceptrons-mlps-activations.md), and it holds nearly all of a network's weights. Two more layers appear in almost every network, and the syllabus names both. **Batch normalization** keeps a deep stack trainable. **Dropout** stops it from memorizing the training set. Both behave differently in training and in evaluation, which is where most of the bugs around them come from. **Layer normalization** is batch normalization with the mean and variance taken along the other axis, no running statistics, and the same computation in training and evaluation. It is what Transformers use.

Contests ask for these by hand and as code. In [2026 Round 1](https://www.usaaio.org/attachments/past-problems/2026/usaaio-2026-round-1-problems.pdf), Problem 7 had you write a threshold layer and a linear layer as your own `nn.Module` subclasses and assemble a classifier that only predicts and is never trained. In [2026 Round 2, Day 2](https://www.usaaio.org/attachments/past-problems/2026/usaaio-2026-round-2-day-2-problems.pdf), Problem 4 banned pretrained weights and gave 200 labels, so a from-scratch model had to be regularized to avoid memorizing them.

## Example: BatchNorm on a batch of three

A `BatchNorm1d` layer with one feature has $\gamma = 2$, $\beta = 1$, $\varepsilon = 10^{-5}$, momentum 0.1, and fresh running statistics (mean 0, variance 1). In training mode it receives the batch $x = (1, 2, 6)$. The task: compute (a) its three outputs, (b) the running mean and running variance after this batch (PyTorch updates the running variance with the batch variance that divides by $N - 1$), and (c) its outputs on the same batch in eval mode.

The problem asks for the forward pass of one normalization layer, in both of its modes, on numbers small enough to do by hand. The explanation defines the layer and the implementation checks every number against PyTorch.

## Explanation

### Why plain stacks fail

Take a network of twenty hidden linear layers with a ReLU after each, plus a linear output layer. Train it with plain gradient descent on a task a two-layer network solves easily: class 1 when the two coordinates of a point have the same sign. Then add one normalization layer after each hidden layer except the first and change nothing else:

```python
import torch
from torch import nn

def deep_mlp(depth, normalize, width=32):
    layers = [nn.Linear(2, width), nn.ReLU()]
    for _ in range(depth - 1):
        layers.append(nn.Linear(width, width))
        if normalize:
            layers.append(nn.BatchNorm1d(width))
        layers.append(nn.ReLU())
    layers.append(nn.Linear(width, 2))
    return nn.Sequential(*layers)

torch.manual_seed(0)
X = torch.rand(2000, 2) * 2 - 1
y = ((X[:, 0] * X[:, 1]) > 0).long()          # class 1 when the signs agree

def train(depth, normalize, steps=400):
    torch.manual_seed(0)
    model = deep_mlp(depth, normalize)
    opt = torch.optim.SGD(model.parameters(), lr=0.05)
    loss_fn = nn.CrossEntropyLoss()
    for _ in range(steps):
        loss = loss_fn(model(X), y)
        opt.zero_grad()
        loss.backward()
        opt.step()
    model.eval()
    with torch.no_grad():
        acc = (model(X).argmax(1) == y).float().mean().item()
    return acc, model[0].weight.grad.abs().mean().item()

for depth in (2, 20):
    for normalize in (False, True):
        acc, g = train(depth, normalize)
        print(f"depth {depth:2d}  batchnorm {str(normalize):5s}  accuracy {acc:.3f}  first-layer gradient {g:.1e}")
```

```output
depth  2  batchnorm False  accuracy 0.946  first-layer gradient 4.6e-03
depth  2  batchnorm True   accuracy 0.984  first-layer gradient 1.4e-02
depth 20  batchnorm False  accuracy 0.504  first-layer gradient 4.2e-10
depth 20  batchnorm True   accuracy 0.998  first-layer gradient 3.9e-03
```

At depth 20 the plain network sits at chance, and the last column says why. The gradient reaching its first layer is $4 \times 10^{-10}$, so the early layers receive almost no signal. That is the vanishing gradient, measured. With normalization the same network gets 99.8%, and the first-layer gradient is about ten million times larger. Each normalization layer resets its input to a fixed scale, so no layer's output drifts into the range where the next activation function has no slope. The other standard fix for depth is the residual connection, which adds a layer's input back to its output. ResNets and Transformers use it together with normalization, and [Build a Vision Model: Deeper networks](2.25-CV12-vision-classify.md#lesson-deeper-networks) covers it.

### Batch normalization

Batch normalization gives each feature mean 0 and variance 1 across the current batch, then lets the network rescale it. For one feature with values $x_1, \dots, x_N$ in the batch, the forward pass is three steps.

**Step 1.** Take the mean and the variance of the feature over the batch, the variance dividing by $N$:

$$
\begin{aligned}
\mu_B &= \frac{1}{N}\sum_{i=1}^{N} x_i, \\
\sigma_B^2 &= \frac{1}{N}\sum_{i=1}^{N} (x_i - \mu_B)^2 .
\end{aligned}
$$

**Step 2.** Normalize: subtract the mean and divide by the standard deviation, with a small $\varepsilon$ to keep the division safe:

$$
\hat{x}_i = \frac{x_i - \mu_B}{\sqrt{\sigma_B^2 + \varepsilon}} .
$$

**Step 3.** Scale and shift with two learnable numbers per feature, $\gamma$ and $\beta$:

$$
y_i = \gamma\,\hat{x}_i + \beta .
$$

The last step means the layer loses nothing. If zero mean and unit variance is the wrong scale for a feature, training can set $\gamma = \sqrt{\sigma_B^2 + \varepsilon}$ and $\beta = \mu_B$ and get the input back. A `BatchNorm1d` over $d$ features has $2d$ trainable parameters. For images, `nn.BatchNorm2d` does the same per channel, with the mean and variance taken over the batch and over every pixel position.

<ProblemCard id="cl-batchnorm-parameter-count" />

For the example, $\mu_B = 3$, $\sigma_B^2 = (4 + 1 + 9)/3 = 14/3$, and $\sqrt{14/3 + 10^{-5}} = 2.160$, so $\hat{x} = (-0.926, -0.463, 1.389)$ and $y = 2\hat{x} + 1 = (-0.852, 0.074, 3.777)$. That is part (a).

**Training and evaluation differ.** In training, $\mu_B$ and $\sigma_B^2$ come from the batch in front of the layer. At evaluation the batch may be one example, which has no meaningful mean or variance. So during training the layer also keeps running averages,

$$
\begin{aligned}
\mu_\text{run} &\leftarrow (1 - m)\,\mu_\text{run} + m\,\mu_B, \\
\sigma_\text{run}^2 &\leftarrow (1 - m)\,\sigma_\text{run}^2 + m\,\sigma_B^2 ,
\end{aligned}
$$

with momentum $m = 0.1$ in PyTorch, and PyTorch feeds the variance that divides by $N - 1$ into the second one. For the example that is $\mu_\text{run} = 0.9 \cdot 0 + 0.1 \cdot 3 = 0.3$ and $\sigma_\text{run}^2 = 0.9 \cdot 1 + 0.1 \cdot 7 = 1.6$. That is part (b).

In eval mode the running statistics replace the batch statistics, and the layer becomes a fixed scale and shift, the same for every input. The same batch gives $y_i = 2\,(x_i - 0.3)/\sqrt{1.6 + 10^{-5}} + 1 = (2.107, 3.688, 10.012)$. That is part (c). The numbers are far from the training-mode outputs because the running statistics have seen one batch and still mostly reflect their starting values. A network uses `model.eval()` to make the switch, and forgetting it is the usual bug: [Writing a Training Loop](1.26-PY10-training-loop-in-pytorch.md) covers when to call it.

<ProblemCard id="cl-eval-mode-statistics" />

Without the switch, the layer keeps normalizing each evaluation batch by that batch's own mean and variance, so a prediction depends on the rest of its batch. Evaluation batches are often built differently from training batches, for example unshuffled and sorted by class. In a batch that holds one class, the mean that gets subtracted is that class's own mean, so what sets the class apart is normalized away. Every forward pass in training mode also updates the running averages. A pass over class-sorted batches can skew them toward the last classes it saw, which hurts later predictions even in eval mode.

Why it helps is still argued. The original paper's reason was that each layer's inputs keep shifting as the layers below it change, and normalization holds them still. Later work (Santurkar et al., 2018) found that it mostly smooths the loss surface, so larger learning rates are safe. Either way, training is faster and steadier, and the noise from one batch to the next works a little against overfitting.

### Layer normalization

Everything above depends on the batch. One example's output depends on the others in its batch, the mean and variance are noisy for small batches, and a batch of one has no variance at all. Layer normalization changes one thing, the axis the statistics run along. It normalizes each example across its own features:

$$
\begin{aligned}
\mu &= \frac{1}{d}\sum_{j=1}^{d} x_j, \qquad
\sigma^2 = \frac{1}{d}\sum_{j=1}^{d} (x_j - \mu)^2, \\[4pt]
y &= \gamma \odot \frac{x - \mu}{\sqrt{\sigma^2 + \varepsilon}} + \beta .
\end{aligned}
$$

Here $x$ is one example's $d$ features, $\gamma$ and $\beta$ hold one learnable number per feature, and $\odot$ multiplies entry by entry.

<Figure src="assets/module-media/normalization-axes.svg" alt="Two copies of a grid of N rows by d columns. On the left one column is outlined and labeled as the slice BatchNorm takes its mean and variance over. On the right one row is outlined as the slice LayerNorm uses.">
The same block of activations, $N$ examples by $d$ features. BatchNorm averages down a column, LayerNorm across a row.
</Figure>

One example in, one example out, so batch size never enters, training and evaluation are the same computation, and there are no running statistics. That is why Transformers use it. A sequence of 1,000 tokens is 1,000 separate normalizations, and generation runs one token at a time. The same example in two different batches shows the difference:

```python
import numpy as np

def batchnorm(x, eps=1e-5):
    return (x - x.mean(axis=0)) / np.sqrt(x.var(axis=0) + eps)       # down the batch

def layernorm(x, eps=1e-5):
    return (x - x.mean(axis=-1, keepdims=True)) / np.sqrt(           # across features
        x.var(axis=-1, keepdims=True) + eps)

rng = np.random.default_rng(0)
target = rng.normal(size=4)                                      # the example to watch
batch_a = np.vstack([target, rng.normal(size=(3, 4))])
batch_b = np.vstack([target, rng.normal(size=(7, 4)) * 5 + 2])   # different company

print("BatchNorm  A:", np.round(batchnorm(batch_a)[0], 4))
print("BatchNorm  B:", np.round(batchnorm(batch_b)[0], 4))
print("LayerNorm  A:", np.round(layernorm(batch_a)[0], 4))
print("LayerNorm  B:", np.round(layernorm(batch_b)[0], 4))
```

```output
BatchNorm  A: [1.0936 0.3065 0.6178 0.0246]
BatchNorm  B: [-0.0709 -1.1405 -0.3644 -0.9323]
LayerNorm  A: [-0.2093 -1.1238  1.6163 -0.2832]
LayerNorm  B: [-0.2093 -1.1238  1.6163 -0.2832]
```

BatchNorm gives the same input two different answers depending on its neighbors. LayerNorm never consults them.

**RMSNorm** drops the mean subtraction and keeps only the rescaling, $y = \gamma \odot x / \sqrt{\frac{1}{d}\sum_j x_j^2 + \varepsilon}$. It computes one statistic instead of two, so it is a little cheaper, as good in practice, and several current large language models use it in place of LayerNorm. The two agree exactly when the input already has zero mean.

### Dropout

Dropout works against overfitting. During training it sets each activation to zero with probability $p$, independently of the others. No unit can rely on any particular other unit being present, so the network spreads what it learns over many units. At evaluation nothing is dropped. The one detail to get right is keeping the scale of the activations the same in both modes.

Modern frameworks use **inverted dropout**: scale at training time so that evaluation can do nothing. Draw a random mask and divide the survivors by $1 - p$,

$$
\tilde{x}_i = \frac{m_i}{1 - p}\,x_i,
$$

where the mask $m_i$ is 1 with probability $1 - p$ (kept) and 0 otherwise. On average $m_i$ is $1 - p$, so on average $\tilde{x}_i$ is $x_i$. The activations a layer sees in training have the same mean as the undropped ones it sees at evaluation. The rescaling preserves the expected activation at that operation, not every downstream nonlinear prediction. A drop rate of 0.5 was the original default for fully connected layers, and 0.1 to 0.3 is typical today. Dropout has no parameters.

## Implementation

### The example in PyTorch

`nn.BatchNorm1d(1)` is the layer from the example, with $\gamma$ stored as `weight` and $\beta$ as `bias`. Set them, run the batch in training mode, and the three numbers from part (a) come out, along with the running statistics from part (b):

```python
import torch
from torch import nn

bn = nn.BatchNorm1d(1)                  # one feature, fresh running statistics
with torch.no_grad():
    bn.weight.fill_(2.0)                # gamma
    bn.bias.fill_(1.0)                  # beta
x = torch.tensor([[1.], [2.], [6.]])    # a batch of three, one feature each

bn.train()
print(bn(x).squeeze())
print(bn.running_mean.item(), bn.running_var.item())
```

Training mode, then the running mean and variance after one batch:

```output
tensor([-0.8516,  0.0742,  3.7775], grad_fn=<SqueezeBackward0>)
0.30000001192092896 1.600000023841858
```

Switching to eval mode gives part (c):

```python
bn.eval()
print(bn(x).squeeze())
```

The running statistics replace the batch statistics, so each output depends on its own input alone:

```output
tensor([ 2.1068,  3.6879, 10.0125], grad_fn=<SqueezeBackward0>)
```

The output still carries a `grad_fn` because $\gamma$ and $\beta$ are parameters. What changed is that the batch mean and variance are no longer part of the computation.

### A layer is an nn.Module

The built-in layers are classes like the `MLP` class in the perceptron module, and a contest can ask you to write one. A from-scratch `BatchNorm1d` needs three things the `MLP` did not: two parameters that are not inside an `nn.Linear`, two running statistics that are saved with the model but never trained, and a forward pass that checks which mode it is in:

```python
class BatchNorm(nn.Module):
    def __init__(self, num_features, eps=1e-5, momentum=0.1):
        super().__init__()
        self.gamma = nn.Parameter(torch.ones(num_features))      # trained
        self.beta = nn.Parameter(torch.zeros(num_features))      # trained
        self.register_buffer("running_mean", torch.zeros(num_features))   # saved, not trained
        self.register_buffer("running_var", torch.ones(num_features))
        self.eps, self.momentum = eps, momentum

    def forward(self, x):                                        # x: (N, num_features)
        if self.training:
            mean = x.mean(dim=0)
            var = x.var(dim=0, unbiased=False)
            with torch.no_grad():
                self.running_mean.mul_(1 - self.momentum).add_(self.momentum * mean)
                self.running_var.mul_(1 - self.momentum).add_(self.momentum * x.var(dim=0, unbiased=True))
        else:
            mean, var = self.running_mean, self.running_var
        x_hat = (x - mean) / torch.sqrt(var + self.eps)
        return self.gamma * x_hat + self.beta
```

- `nn.Parameter` marks a tensor as trainable: `parameters()` returns it and
  the optimizer updates it.
- `register_buffer` stores a tensor on the module without making it a
  parameter. It travels with the model, into `state_dict()` and onto a GPU,
  but no gradient ever touches it. Running statistics are the standard use.
- `self.training` is the flag that `model.train()` and `model.eval()` set on
  every module inside the model. The forward pass reads it and nothing else
  changes.
- The running update sits inside `torch.no_grad()` because it is bookkeeping,
  not part of the function being differentiated.

Checked against PyTorch's own layer in both modes:

```python
torch.manual_seed(0)
xb = torch.randn(8, 4) * 3 + 1
mine, ref = BatchNorm(4), nn.BatchNorm1d(4)

mine.train(); ref.train()
print(torch.allclose(mine(xb), ref(xb), atol=1e-6))
print(torch.allclose(mine.running_var, ref.running_var))
mine.eval(); ref.eval()
print(torch.allclose(mine(xb), ref(xb), atol=1e-6))
```

Training-mode outputs, running variances, and eval-mode outputs all agree:

```output
True
True
True
```

### Dropout from scratch

Dropout has no parameters and no buffers, so the whole layer is the mode check and one masked multiply:

```python
class Dropout(nn.Module):
    def __init__(self, p=0.5):
        super().__init__()
        self.p = p

    def forward(self, x):
        if not self.training:
            return x                                  # evaluation: identity
        mask = (torch.rand_like(x) >= self.p).float()
        return x * mask / (1 - self.p)                # inverted dropout

torch.manual_seed(0)
drop = Dropout(0.3)
drop.train()
out = drop(torch.ones(100000))
print((out == 0).float().mean().item(), out.mean().item(), out.max().item())
```

About 30% of the entries are zeroed, the survivors are scaled to $1 / 0.7 = 1.43$, and the mean stays at 1 in expectation (the printed 1.0022 is sample noise over 100,000 draws):

```output
0.2984600067138672 1.0022001266479492 1.4285714626312256
```

### The built-ins in a network

In practice the three layers are `nn.BatchNorm1d`, `nn.LayerNorm` and `nn.Dropout`, placed between the linear layers of a network. The usual order in a fully connected block is linear, normalization, activation, dropout:

```python
model = nn.Sequential(
    nn.Linear(784, 256), nn.BatchNorm1d(256), nn.ReLU(), nn.Dropout(0.2),
    nn.Linear(256, 10),
)
```

Every module in the stack reads the same `training` flag, so one call to `model.eval()` before measuring accuracy switches all of them, and `model.train()` switches them back. The bias of a linear layer that feeds a batch norm does nothing, because the mean subtraction removes it, so that layer is often built with `bias=False`.
