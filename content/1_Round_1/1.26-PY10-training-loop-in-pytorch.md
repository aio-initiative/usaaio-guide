## Overview

Training a network is one loop. Take a batch of examples, run the forward pass, measure the loss, run the backward pass, update the parameters, and repeat until the data has been seen a few times over. Five lines of PyTorch do the step, and the rest of the loop is what surrounds them: data arriving in batches, an evaluation pass that measures without training, and a record of how the loss moved.

Most deep learning problems on the olympiad need this loop written from memory, for whatever model and loss the problem hands you. In [2026 Round 2](https://www.usaaio.org/attachments/past-problems/2026/usaaio-2026-round-2-day-1-problems.pdf) the loss measured how far the output was from satisfying a physics equation, and in [Round 2, Day 2](https://www.usaaio.org/attachments/past-problems/2026/usaaio-2026-round-2-day-2-problems.pdf) the labels came from the model's own predictions, but the loop around them was this one. Round 1 is CPU-only, so it also has to be fast enough without a GPU.

## Example: train the digit classifier properly

The task: train a 784-128-10 ReLU network on MNIST the way a contest solution should. Hold out part of the training images for validation, feed the rest in shuffled batches from a `DataLoader`, write the training step and the evaluation as functions, and run the epoch loop while recording the training and validation curves. The same code on only 2,000 images shows the turn, and the figure below plots it: the validation loss rises after 13 epochs while the training loss keeps falling.

[The Multilayer Perceptron](1.18-DL1-neural-networks-perceptrons-mlps-activations.md) trained its network with a loop written out by hand, sliced from a tensor. This task asks for the same thing done properly: data in batches from a loader, a validation set the model never trains on, the step and the evaluation as functions, and a record of each epoch. The explanation takes the pieces in order and the implementation assembles them.

## Explanation

### The five lines

One training step on one batch `xb` with labels `yb`:

```python
logits = model(xb)            # 1. forward pass
loss = loss_fn(logits, yb)    # 2. one number saying how wrong the batch was
optimizer.zero_grad()         # 3. clear the gradients left from the last step
loss.backward()               # 4. backpropagation fills every parameter's .grad
optimizer.step()              # 5. move every parameter against its gradient
```

Line 1 records a computation graph as it runs, because the parameters have `requires_grad=True`. Line 2 reduces the batch to one number, which is what `backward()` needs. Line 4 is the backward pass from [Backpropagation by Hand](2.1-MA4-backpropagation-mechanics.md), run by autograd, and it writes $\partial L / \partial \theta$ into `.grad` for every parameter $\theta$. Line 5 reads those gradients and applies the update rule, $\theta \leftarrow \theta - \eta\, \partial L / \partial \theta$ for plain SGD, where $\eta$ is the learning rate.

<ProblemCard id="tl-backward-fills-grad" />

Line 3 is the one that looks optional and is not. PyTorch adds each `backward()` into `.grad` instead of replacing it, so without the clear, every step would move the parameters by the sum of every gradient so far. The order is fixed by what each line needs: the loss before `backward()`, the clear before `backward()`, and `step()` after it. Putting `zero_grad()` first in the block, as many tutorials do, is the same loop.

### Batches from a DataLoader

A `Dataset` answers two questions, how many examples there are and what example $i$ is, through `__len__` and `__getitem__`. For data already in tensors, `TensorDataset(X, y)` is that class. A `DataLoader` wraps a dataset and hands out batches:

```python
loader = DataLoader(TensorDataset(X, y), batch_size=64, shuffle=True)
```

Iterating over it yields `(xb, yb)` pairs of 64 examples at a time, in a new random order every epoch when `shuffle=True`, with a last batch that holds whatever is left. `len(loader)` is the number of batches. A last batch of one example makes `BatchNorm1d` raise, so training loaders often pass `drop_last=True`. Default collation stacks tensors along a new dimension 0, which requires every example to have the same shape, so variable-length sequences need a custom `collate_fn` that pads. A batch of 64 gives a gradient that is a noisy estimate of the full-data gradient, and that noise is the price of taking hundreds of steps per pass instead of one. One pass over the loader is an **epoch**.

When the data is a folder of files and not a tensor, write the `Dataset` yourself: `__getitem__` loads file $i$ and returns its tensor and label, and the loader does the batching. With files, `num_workers=2` or more loads the batches in background processes, so the model is not left waiting on the disk. The implementation writes one.

### Loss function and optimizer

`nn.CrossEntropyLoss()` takes the raw scores from the model and integer labels of dtype `long`, applies the softmax itself, and returns the mean cross-entropy over the batch. Putting a softmax in the model before it is a common mistake: the loss applies a second one, and training slows to a crawl without an error. [Loss Functions](1.28-ML9-loss-functions.md) has the other losses and when each applies.

Three kinds of output cover nearly every problem, and the loss fixes the shape and dtype of the model's output and of the target:

| Task | Model output | Target | Loss |
|---|---|---|---|
| One of $K$ classes | $(N, K)$ scores | $(N,)$ integers, dtype `long` | `nn.CrossEntropyLoss` |
| Yes or no | $(N,)$ score | $(N,)$ floats, 0 or 1 | `nn.BCEWithLogitsLoss` |
| A number | $(N,)$ | $(N,)$ floats | `nn.MSELoss` |

The first two take raw scores and apply the softmax or the sigmoid inside, in a form that cannot overflow, so the model's last layer stays linear in every case. The third needs its two shapes equal: an $(N, 1)$ prediction against an $(N,)$ target broadcasts to an $N \times N$ table of differences, and PyTorch warns but computes it. A loss is any single number computed from tensors, so a problem that defines its own, as the physics problem in 2026 Round 2 did, needs one function and nothing else. The implementation writes cross-entropy out as one to show the form.

The optimizer owns the update rule. It is built from the parameters it is allowed to change and a learning rate:

```python
optimizer = torch.optim.Adam(model.parameters(), lr=1e-3)
```

`SGD` is the plain step. `Adam` scales each parameter's step by its own gradient history, trains well at `lr=1e-3` on most problems, and is the default to reach for. [Optimizers & Training Tricks](1.21-DL4-optimization-adam-sgd.md) is about the difference.

### Evaluation

Measuring accuracy is a forward pass with two switches thrown. `model.eval()` tells layers that behave differently in training, dropout and batch normalization, to use their evaluation behavior, and `model.train()` switches them back. `torch.no_grad()` stops autograd recording, which saves the memory and time of a graph nobody will call `backward()` on. The numbers are the same either way for a plain MLP, and wrong without `model.eval()` for a network with dropout.

<ProblemCard id="tl-train-and-eval" />

The evaluation data has to be data the model did not train on. Split a **validation set** off the training data and use it after every epoch to watch for overfitting and to choose between runs. The **test set** is used once, at the end, on the model the validation set picked. A test score that was consulted during training is a validation score with a misleading name.

### Epochs and curves

<Figure src="assets/module-media/training-loop-flow.svg" alt="A flow diagram. Inside a dashed box labeled for each epoch, a dashed box labeled for each batch holds the five steps forward pass, loss, zero_grad, backward, step in a column, followed below by a box labeled evaluate on validation.">
Two nested loops. The inner one runs the five steps on every batch, and the outer one evaluates after every pass.
</Figure>

Record the training loss and the validation loss after every epoch. Both falling means the model is still learning. Training loss falling while validation loss rises means it has started memorizing the training set, and the epoch with the lowest validation loss, or the highest validation accuracy, is the model to keep. But first compare the two measurements: training may include dropout, augmentation, or a penalty that validation omits. Losses computed under different conditions are not directly interchangeable. On 2,000 MNIST images, a 784-128-10 network reaches that point after 13 epochs:

<Figure src="assets/module-media/training-curves.svg" alt="Training loss and validation loss over 40 epochs. The training loss falls toward zero. The validation loss falls to its minimum at epoch 13 and then climbs slowly.">
Trained on 2,000 images, the training loss keeps falling for 40 epochs while the validation loss turns around after 13. Everything after that is memorization.
</Figure>

Keeping a copy of the parameters at the best epoch, `copy.deepcopy(model.state_dict())`, and restoring it at the end is the simplest form of **early stopping**, and it costs nothing.

The curves are also where a broken run first shows itself:

| What the curves show | What it usually means |
|---|---|
| The loss is `nan`, or jumps up and stays there | The learning rate is too high, or the gradients are exploding |
| The loss sits near $\ln K$, the value for guessing evenly among $K$ classes, and never moves | The learning rate is too low, every unit is dead, or the labels do not line up with the outputs |
| Training loss falls while validation loss rises | Memorizing: stop at the turn, add dropout, or get more data |
| Both fall, slowly, every epoch | Underfitting: a bigger model, a higher learning rate, or more epochs |

When the diagnosis is overfitting, the fixes in order of expected value are: early stopping (free), augmentation, more data, then dropout or a weight-decay penalty, then a smaller model. Lowering the learning rate is *not* on the list. It fits the noise more precisely, not less.

## Implementation

### Data

Flatten and scale the images as before, then split off the validation set with a random permutation and wrap each split in a loader:

```python
import torch
from torch import nn
from torch.utils.data import DataLoader, TensorDataset
from torchvision import datasets

train = datasets.MNIST("data", train=True, download=True)
test = datasets.MNIST("data", train=False, download=True)
X = train.data.reshape(-1, 784).float() / 255
y = train.targets
X_test = test.data.reshape(-1, 784).float() / 255
y_test = test.targets

torch.manual_seed(0)
perm = torch.randperm(60000)
train_idx, val_idx = perm[:50000], perm[50000:]
train_loader = DataLoader(TensorDataset(X[train_idx], y[train_idx]), batch_size=64, shuffle=True)
val_loader = DataLoader(TensorDataset(X[val_idx], y[val_idx]), batch_size=1000)
test_loader = DataLoader(TensorDataset(X_test, y_test), batch_size=1000)

print(len(train_loader), len(val_loader))
xb, yb = next(iter(train_loader))
print(xb.shape, yb.shape, yb.dtype)
```

782 training batches of 64 (the last one has 16), 10 validation batches of 1,000, and a batch is one tensor of rows plus one tensor of integer labels:

```output
782 10
torch.Size([64, 784]) torch.Size([64]) torch.int64
```

Evaluation loaders need no shuffling and can use bigger batches, since nothing is stored for a backward pass. `torch.utils.data.random_split(dataset, [50000, 10000])` makes a split of the same sizes in one call, drawing its own permutation, so the validation examples are not the same ones as above.

`TensorDataset` is the wrapper for data that is already a tensor. When it is not, a NumPy array per example or a folder of image files, the `Dataset` is written by hand. It needs `__len__` and `__getitem__`, and the loader does the batching, the shuffling, and the collection of the labels into a tensor:

```python
from torch.utils.data import Dataset

class DigitsFromArrays(Dataset):
    def __init__(self, images, labels):           # images: (N, 28, 28) uint8, labels: (N,)
        self.images, self.labels = images, labels

    def __len__(self):
        return len(self.labels)

    def __getitem__(self, i):                     # example i as (tensor, label)
        x = torch.as_tensor(self.images[i], dtype=torch.float32).reshape(784) / 255
        return x, int(self.labels[i])

dataset = DigitsFromArrays(train.data.numpy(), train.targets.numpy())
loader = DataLoader(dataset, batch_size=64, shuffle=True)
xb, yb = next(iter(loader))
print(len(dataset), len(loader), xb.shape, yb.shape, yb.dtype)
```

```output
60000 938 torch.Size([64, 784]) torch.Size([64]) torch.int64
```

Sixty thousand examples, 938 batches, and the same batch layout as before. A dataset of files differs only inside `__getitem__`, which opens and decodes file $i$ there.

### Model, loss, optimizer

```python
class MLP(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1 = nn.Linear(784, 128)
        self.fc2 = nn.Linear(128, 10)

    def forward(self, x):
        return self.fc2(torch.relu(self.fc1(x)))

torch.manual_seed(0)
model = MLP()
loss_fn = nn.CrossEntropyLoss()
optimizer = torch.optim.Adam(model.parameters(), lr=1e-3)
```

`loss_fn` is a function of two tensors that returns one number `backward()` can be called on, and a loss written by hand is the same thing. Cross-entropy is the mean negative log-probability of the true class, and `log_softmax` computes it without the overflow a plain softmax risks:

```python
def my_loss(logits, yb):
    return -torch.log_softmax(logits, dim=1)[torch.arange(len(yb)), yb].mean()

logits = torch.tensor([[2., 0., -1.], [1., 1., 3.]])
yb = torch.tensor([0, 1])
print(f"{my_loss(logits, yb).item():.4f} {loss_fn(logits, yb).item():.4f}")
```

The two agree, and either can go in the loop below:

```output
1.2047 1.2047
```

### A check before training

With random weights the network has no reason to prefer any digit, so every class should get about a tenth of the probability and the loss should sit near $\ln 10 = 2.303$:

```python
with torch.no_grad():
    scores = model(X[val_idx])
print(f"{loss_fn(scores, y[val_idx]).item():.4f} {(scores.argmax(dim=1) == y[val_idx]).float().mean().item():.4f}")
```

It does, and the accuracy is chance:

```output
2.3028 0.1068
```

A starting loss far above $\ln K$ means the scores are too large before any training has happened, from an initialization at the wrong scale or a stray softmax. The same network with its weights multiplied by ten starts at 10.3. That is a fault in the model, not the loop. The other check, training on one batch of 64 until the loss reaches zero, proves the loop can fit anything at all before it is trusted on 50,000 images.

### The step and the evaluation as functions

Each is a loop over a loader. `train_step` runs the five lines on every batch and returns the mean training loss. `evaluate` runs the forward pass only, under the two switches, and returns the mean loss and the accuracy:

```python
def train_step(model, loader, loss_fn, optimizer):
    """One pass over the training data. Returns the mean training loss."""
    model.train()
    total = 0.0
    for xb, yb in loader:
        logits = model(xb)                # 1. forward pass
        loss = loss_fn(logits, yb)        # 2. loss on this batch
        optimizer.zero_grad()             # 3. clear the old gradients
        loss.backward()                   # 4. backpropagate
        optimizer.step()                  # 5. update the parameters
        total += loss.item() * len(xb)
    return total / len(loader.dataset)

def evaluate(model, loader, loss_fn):
    """Mean loss and accuracy over a loader, with no training side effects."""
    model.eval()
    total, correct = 0.0, 0
    with torch.no_grad():
        for xb, yb in loader:
            logits = model(xb)
            total += loss_fn(logits, yb).item() * len(xb)
            correct += (logits.argmax(dim=1) == yb).sum().item()
    return total / len(loader.dataset), correct / len(loader.dataset)
```

Two details are deliberate. `loss.item()` turns the batch loss into a plain number before it is added up, so the running total does not keep every batch's computation graph alive. And each batch's mean loss is weighted by its size, `len(xb)`, so the short last batch does not count as much as a full one.

### The loop

```python
for epoch in range(5):
    train_loss = train_step(model, train_loader, loss_fn, optimizer)
    val_loss, val_acc = evaluate(model, val_loader, loss_fn)
    print(f"epoch {epoch + 1}  train loss {train_loss:.4f}  val loss {val_loss:.4f}  val acc {val_acc:.4f}")
```

Five epochs take a few seconds on a laptop CPU, and both losses fall every time:

```output

epoch 2  train loss 0.1678  val loss 0.1486  val acc 0.9564
epoch 3  train loss 0.1194  val loss 0.1182  val acc 0.9660
epoch 4  train loss 0.0913  val loss 0.1036  val acc 0.9688
epoch 5  train loss 0.0718  val loss 0.0936  val acc 0.9728
```

The test set, once, at the end:

```python
test_loss, test_acc = evaluate(model, test_loader, loss_fn)
print(f"test acc {test_acc:.4f}")
```

Close to the validation score, as it should be:

```output
test acc 0.9749
```

On a GPU the loop gains two lines. `model.to(device)` goes once, before the optimizer is built, and `xb, yb = xb.to(device), yb.to(device)` goes at the top of both batch loops. Nothing else changes.

### Common mistakes

Most of these run without an error and give a worse model.

- **Missing `optimizer.zero_grad()`.** Gradients pile up across batches. The same network and data reach 93.9% validation accuracy after one epoch with the clear and 77.3% without it.
- **Missing `model.eval()`.** For a model with dropout, the reported accuracy jumps around from run to run of the same evaluation. For batch normalization it is silently wrong instead: each batch is normalized by its own statistics rather than the running ones, so the number depends on how the evaluation data happens to be batched.
- **A softmax before `CrossEntropyLoss`.** The loss applies its own, the gradients flatten, and training is slow for no visible reason.
- **Float labels.** Class-index labels for `CrossEntropyLoss` must be dtype `long`. A float target is read as class probabilities and must have the same shape as the model's output, so a flat float `(N,)` label is rejected, while a float one-hot `(N, K)` target is accepted as a soft label.
- **Logging `loss` instead of `loss.item()`.** Every stored loss keeps its graph, and memory grows with every batch.
- **Tensors on two devices.** When a GPU is in use, the model and every batch have to be moved to it. `RuntimeError: Expected all tensors to be on the same device` is the message.
