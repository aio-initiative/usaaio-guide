## Overview

Scaling laws say bigger models are better, but every parameter in a dense Transformer participates in every token's forward pass, so capacity and cost rise together. **Mixture of experts** breaks that coupling: it makes the model much larger in parameters while keeping the arithmetic per token roughly fixed.

The mechanism is **conditional computation**: for each token, activate only a small chosen subset of the network. A model can then hold hundreds of billions of parameters while any individual token touches only a small fraction of them.

### Where the parameters are

In a standard Transformer block the **feed-forward network** dominates the parameter budget. With $d_{\text{ff}} = 4 d_{\text{model}}$ it holds $8 d_{\text{model}}^2$ weights against attention's $4 d_{\text{model}}^2$, about two thirds of the block. So the FFN is what MoE replaces.

A dense FFN applies the same two matrices to every token:

$$
\text{FFN}(\mathbf{x}) = W_2 \, \sigma(W_1 \mathbf{x})
$$

costing roughly $4 d_{\text{model}} d_{\text{ff}}$ FLOPs per token (counting each multiply-accumulate as two FLOPs). Doubling $d_{\text{ff}}$ doubles both parameters **and** per-token cost.

## The sparse MoE layer

Replace the single FFN with $N$ independent **experts** $E_1, \dots, E_N$, each an ordinary FFN of the same shape, plus a small **router** that decides which experts each token visits.

### Routing

The router is a single learned matrix $W_g \in \mathbb{R}^{N \times d_{\text{model}}}$ that gives each expert a score, and a softmax turns the scores into probabilities:

$$
\mathbf{g}(\mathbf{x}) = \operatorname{softmax}(W_g\, \mathbf{x}) \in \mathbb{R}^N
$$

Keep only the $k$ largest entries, typically $k = 1$ or $2$, and call that set of experts $\mathcal{T}$. The layer output is a weighted sum over just those experts:

$$
\mathbf{y} = \sum_{i \in \mathcal{T}} w_i(\mathbf{x})\, E_i(\mathbf{x}),
$$

where each **gate weight** $w_i$ is computed from the router's probabilities, in one of two ways described below. The accounting is the entire point:

* **Parameters** scale with $N$: all $N$ experts are stored and trained.
* **FLOPs per token** scale with $k$: only $k$ experts run.

With $N = 64$ and $k = 2$ the layer holds 64 FFNs' worth of capacity at twice one FFN's compute: **64× the parameters for 2× the arithmetic**, or 32 times as many parameters per unit of compute.

### The gate weight is what trains the router

Why multiply each chosen expert's output by a weight at all, rather than just adding up the chosen experts? Because the weight is the router's only source of gradient. Picking the top $k$ is a discrete decision with no useful derivative. The weight $w_i$, though, is a smooth function of the router's scores, so $\partial \mathcal{L} / \partial W_g$ exists, and the router learns from how much each chosen expert helped.

Two weightings are in common use, and the difference matters at $k = 1$:

* **Renormalized:** divide the chosen probabilities by their sum, $w_i = g_i / \sum_{j \in \mathcal{T}} g_j$, so the weights add to 1. Mixtral does this with $k = 2$.
* **Raw:** use the softmax probability itself, $w_i = g_i$. Switch Transformers does this with $k = 1$.

Renormalizing a single expert gives $w_i = g_i / g_i = 1$ for every token. The weight is then a constant, the router's parameters reach the output only through which expert wins, and the router gets no gradient at all. The paper that introduced top-$k$ routing had conjectured that a router needs at least two experts per token to learn. Switch Transformers routes each token to one expert and keeps the raw probability as its weight, which leaves the router a gradient.

Nudging every router weight up and down and watching the loss shows all three cases. In the toy code below each expert is a single linear map rather than the two-matrix FFN defined above, which is enough to show how the gate weight trains:

```python
import numpy as np

rng = np.random.default_rng(0)
d, N = 8, 4
x = rng.normal(size=d)                                   # one token
W_g = rng.normal(size=(N, d)) * 0.5                      # the router
experts = rng.normal(size=(N, d, d)) / np.sqrt(d)        # expert i is the linear map experts[i]
target = rng.normal(size=d)

def softmax(z):
    e = np.exp(z - z.max())
    return e / e.sum()

def loss(W_g, k, renormalize):
    g = softmax(W_g @ x)
    chosen = np.argsort(-g)[:k]
    w = g[chosen] / g[chosen].sum() if renormalize else g[chosen]
    y = sum(w_i * (experts[i] @ x) for w_i, i in zip(w, chosen))
    return 0.5 * np.sum((y - target) ** 2)

def router_gradient(k, renormalize, eps=1e-6):
    """Nudge every router weight up and down and measure how the loss responds."""
    G = np.zeros_like(W_g)
    for ij in np.ndindex(W_g.shape):
        step = np.zeros_like(W_g)
        step[ij] = eps
        G[ij] = (loss(W_g + step, k, renormalize) - loss(W_g - step, k, renormalize)) / (2 * eps)
    return G

for k, renormalize in ((1, True), (1, False), (2, True)):
    G = router_gradient(k, renormalize)
    name = "renormalized" if renormalize else "raw"
    print(f"top-{k}, {name:>12} gate: |dL/dW_g| = {np.linalg.norm(G):.3f}")
```

```output
top-1, renormalized gate: |dL/dW_g| = 0.000
top-1,          raw gate: |dL/dW_g| = 0.832
top-2, renormalized gate: |dL/dW_g| = 2.230
```

The zero is exact. Whichever way a router weight is nudged, the chosen expert's weight is still exactly 1, so the loss does not move at all. With two experts the renormalized weights still depend on the scores, since they split 1 between the two in proportion to their probabilities, and the gradient is back.

## Load balancing

The obvious failure mode is the one that actually happens. Nothing above prevents the router from sending most tokens to a handful of experts, and the dynamics actively encourage it: an expert that is slightly better early receives more tokens, trains faster, becomes better still, and attracts yet more traffic. This **rich-get-richer collapse** leaves most experts undertrained and wastes the capacity MoE exists to provide. It is also a throughput disaster, since experts are sharded across devices and an overloaded expert stalls everyone.

### The auxiliary loss

The standard fix adds a differentiable penalty for imbalance. For a batch, let

* $f_i$ = fraction of the batch's assignments that go to expert $i$ (each of its $T$ tokens makes $k$ assignments), so the $f_i$ add to 1,
* $P_i$ = mean router probability assigned to expert $i$.

and add

$$
\mathcal{L}_{\text{aux}} = \alpha\, N \sum_{i=1}^{N} f_i P_i
$$

Note the split of labor: $f_i$ is a hard count and carries no gradient, while $P_i$ is smooth. Their product yields a gradient that pushes probability mass *away* from experts already receiving many tokens. Under a uniform split, $f_i = P_i = 1/N$, so $\sum_i f_i P_i = N \cdot \tfrac{1}{N^2} = \tfrac{1}{N}$, and the loss is $\alpha N \cdot \tfrac{1}{N} = \alpha$. Typical $\alpha \approx 10^{-2}$, large enough to balance and small enough not to distort the language objective.

Concentrating the router usually pushes the loss up, and the reason says when it does. If the token fractions track the probabilities, $f_i = P_i$, the loss is $\alpha N \sum_i P_i^2$, and Cauchy-Schwarz gives $\sum_i P_i^2 \ge 1/N$ with equality only at uniform. But $f$ counts hard top-$k$ choices while $P$ averages soft probabilities, and nothing forces them to agree. Three experts with top-1 routing, half the tokens at probabilities $(0.34, 0.33, 0.33)$ and half at $(0, 0.51, 0.49)$, give $f = (0.5, 0.5, 0)$ and $P = (0.17, 0.42, 0.41)$, a loss of $0.885\,\alpha$, while expert 3 receives no tokens at all. So $\alpha$ is the loss at balance, not a strict floor, and a low loss on its own does not prove the experts are balanced. Monitor $f$ directly.

### Capacity factor

For speed, each expert processes a fixed-size buffer, so it accepts at most

$$
C = \text{CF} \cdot \frac{k\,T}{N}
$$

assignments from a batch of $T$ tokens. Each token makes $k$ assignments, so $kT/N$ is one expert's share under perfect balance, and the **capacity factor** CF adds headroom. Typical training values are 1.0 to 1.25. Switch Transformers, with $k = 1$, writes the formula without the $k$. An assignment that arrives at a full expert is **dropped**. A token that loses all of its assignments skips the layer and passes through the residual connection unchanged.

How much gets dropped depends on how uneven the router is. Here eight experts, each with its own built-in popularity, receive one batch:

```python
rng = np.random.default_rng(1)
N, k, T = 8, 2, 4096
pull = rng.normal(scale=0.5, size=N)                     # each expert's built-in popularity
logits = rng.normal(size=(T, N)) + pull
chosen = np.argsort(-logits, axis=1)[:, :k]              # top-k experts for each token
load = np.bincount(chosen.ravel(), minlength=N)
print("assignments per expert:", load, "  share under perfect balance:", k * T // N)
for cf in (1.0, 1.25, 1.5, 2.0):
    C = int(cf * k * T / N)
    dropped = np.maximum(load - C, 0).sum()
    print(f"CF {cf:<4}  capacity {C:>4}  dropped {dropped:>4} of {k * T} assignments ({dropped / (k * T):.1%})")
```

```output
assignments per expert: [1091 1422 1051  287 1458 1125  537 1221]   share under perfect balance: 1024
CF 1.0   capacity 1024  dropped 1224 of 8192 assignments (14.9%)
CF 1.25  capacity 1280  dropped  320 of 8192 assignments (3.9%)
CF 1.5   capacity 1536  dropped    0 of 8192 assignments (0.0%)
CF 2.0   capacity 2048  dropped    0 of 8192 assignments (0.0%)
```

At CF 1.0 about one assignment in seven is dropped, and 1.25 cuts that to 3.9%. A larger factor drops less but costs more: every buffer grows, and its unused slots are padding that still takes memory, compute and communication. CF is a direct trade between throughput and fidelity, and good balance is what lets it stay small.

### Newer approaches

Two refinements now dominate practice:

* **Fine-grained plus shared experts.** DeepSeekMoE splits experts into many smaller ones, improving the combinatorics of which specialists can combine, and marks a few as **shared**, always active for every token. The shared experts absorb general-purpose computation, freeing the routed ones to specialize rather than each re-learning common features.
* **Balancing without a loss.** The auxiliary loss is a second objective pulling against the first. DeepSeek-V3 instead adds a per-expert **bias** $b_i$ to the routing scores, but only when choosing the top $k$. The gate weights still come from the scores without the bias, so the bias changes where tokens go but not how their outputs are weighted. After each training step, every overloaded expert's bias goes down by a small fixed step $\gamma$ and every underloaded expert's bias goes up. DeepSeek-V3 keeps only a very small auxiliary loss on top, as a guard against extreme imbalance within a single sequence.

The bias rule takes a few lines. The router here is never trained: each step draws a fresh batch of scores in which the experts have fixed, unequal popularity.

```python
rng = np.random.default_rng(3)
N, k, T = 8, 2, 4096
pull = np.linspace(-1.0, 1.0, N)                         # expert 7 is the most popular, expert 0 the least
bias, gamma = np.zeros(N), 0.01

for step in range(1001):
    scores = rng.normal(size=(T, N)) + pull              # a fresh batch of router scores
    chosen = np.argsort(-(scores + bias), axis=1)[:, :k] # the bias decides who is chosen...
    gates = np.take_along_axis(scores, chosen, axis=1)   # ...but the gates use the raw scores
    load = np.bincount(chosen.ravel(), minlength=N) / (k * T / N)
    if step in (0, 50, 200, 1000):
        print(f"step {step:>4}: load per expert / fair share = {np.round(load, 2)}")
    bias += gamma * np.sign(1.0 - load)                  # starved experts up, busy experts down

print("bias + pull after training:", np.round(bias + pull, 2))
```

```output
step    0: load per expert / fair share = [0.15 0.24 0.42 0.63 0.98 1.38 1.83 2.37]
step   50: load per expert / fair share = [0.44 0.7  1.   0.97 0.93 1.01 1.23 1.71]
step  200: load per expert / fair share = [1.02 0.99 1.06 1.   0.98 1.02 0.95 0.96]
step 1000: load per expert / fair share = [0.94 1.03 1.01 1.01 1.   0.99 1.02 1.01]
bias + pull after training: [-0.01 -0.03 -0.04 -0.03 -0.04 -0.05 -0.04 -0.03]
```

At the start the most popular expert gets 2.37 times its fair share and the least popular 0.15 times. By step 200 every expert is within 6% of fair. The last line shows how: each bias has settled at nearly the negative of its expert's built-in pull, up to a constant shared by all, so the biased scores favor no one.

## Systems reality

MoE is as much a distributed-systems technique as a modeling one. Experts are usually spread across devices, one or a few per device (**expert parallelism**), so routing becomes communication: every device must send each token to wherever its chosen experts live, and collect the results back. That is an **all-to-all** collective, twice per MoE layer, and it is usually the throughput bottleneck. It explains several design choices that otherwise look arbitrary:

* **Small $k$.** Each token is sent to $k$ experts, so communication grows in proportion to $k$.
* **MoE in only some blocks.** GShard and the Switch Transformer experiments put an MoE layer in every other block rather than every block.
* **Strict capacity limits.** Fixed-size buffers keep the communication pattern predictable.

The other cost is memory. All $N$ experts must be resident even though each token uses $k$, so an MoE model needs memory proportional to its **total** parameters while running at the speed of its **active** parameters. MoE buys compute efficiency with memory, not for free.

Mixtral 8x7B makes this concrete. It stores 46.7 billion parameters and uses 12.9 billion of them for each token. The name suggests $8 \times 7 = 56$ billion, but only the feed-forward networks exist eight times over. Attention, the norms and the embeddings are shared by all the experts.

## From scratch

Routing and the balance loss are both short enough to write directly, and seeing the loss respond to a collapsing router makes the mechanism concrete.

```python
import numpy as np

def softmax(x, axis=-1):
    x = x - x.max(axis=axis, keepdims=True)
    e = np.exp(x)
    return e / e.sum(axis=axis, keepdims=True)

def route(logits, k=2):
    """Top-k gate, renormalized over the chosen experts."""
    probs = softmax(logits)
    idx = np.argsort(-probs, axis=-1)[:, :k]
    gates = np.take_along_axis(probs, idx, axis=-1)
    return idx, gates / gates.sum(-1, keepdims=True), probs

def balance_loss(idx, probs, n_experts, alpha=1e-2):
    """alpha * N * sum_i f_i * P_i, which equals alpha when routing is uniform."""
    counts = np.bincount(idx.ravel(), minlength=n_experts)
    f = counts / counts.sum()          # hard assignment fractions, no gradient
    P = probs.mean(axis=0)             # mean router probability, differentiable
    return alpha * n_experts * float(f @ P)

N, T = 8, 512
rng = np.random.default_rng(2)

balanced = rng.normal(size=(T, N)) * 0.1
idx, _, probs = route(balanced)
print(f"balanced  loss = {balance_loss(idx, probs, N):.4f}")

collapsed = balanced.copy()
collapsed[:, 0] += 5.0                 # expert 0 wins nearly everything
idx, _, probs = route(collapsed)
print(f"collapsed loss = {balance_loss(idx, probs, N):.4f}")
```

```output
balanced  loss = 0.0100
collapsed loss = 0.0384
```

The balanced router gives `0.0100`, which is $\alpha$ to four decimal places, the value derived earlier for uniform routing. The derivation gives that value at any expert count: under uniform routing $\sum_i f_i P_i = N \cdot \tfrac{1}{N^2} = \tfrac{1}{N}$, and the $N$ in front cancels it. Tilting one expert's logits pushes the loss to nearly four times that.

The two lines computing `f` and `P` are worth staring at. `f` comes from `bincount` on discrete top-$k$ choices: a hard integer count with no derivative anywhere. `P` is a mean of softmax outputs, smooth in the router weights. Their product is what makes the penalty trainable: `f` weights the penalty toward overloaded experts, and the gradient flows entirely through `P`.
