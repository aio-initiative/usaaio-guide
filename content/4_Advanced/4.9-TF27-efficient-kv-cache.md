## KV cache

### The problem

Part 1 showed that the keys and values of earlier tokens never change. So they can be computed once and kept. Keeping them costs memory, and the amount adds up.

There is a key and a value for every token, in every key-value head, in every layer, and a separate set for every conversation the model is serving. For example, in Llama 2 70B one token costs 320 KiB of cache. A 4,096-token conversation needs 1.25 GiB, and 256 conversations at once need 320 GiB, more than twice the 140 GB of the model's weights.

<Figure src="assets/module-media/efficient-problem-cache.svg" alt="A plot of cache size in GiB against the number of tokens in one conversation with Llama 2 70B. The line rises steadily, by 320 KiB for every token, and reaches 1.25 GiB at 4,096 tokens.">
The cache of one conversation grows with every token.
</Figure>

So the questions are what exactly has to be kept, and how much it costs to keep it.

### Earlier approaches

#### Recompute everything

This is the waste measured in part 1: 333,833,500 scores per head for a 1,000-token reply instead of 500,500, so 333,333,000 of them are thrown away.

#### Keep everything

Keeping every number computed for earlier tokens would also avoid recomputation, but their queries, scores and weights are never used again. Later tokens need the key of "the", (1.000, 0.000) in head 1, but never its query.

### The KV cache

**What is kept.** The **KV cache** keeps only the keys and values of earlier tokens. Each decode run computes the new token's query, key and value, adds the key and value to the cache, and compares the query with every cached key. For example, after "the cat sat" the cache holds 3 keys and 3 values per head, and decoding "on" adds a fourth of each.

<Figure src="assets/module-media/efficient-kv-cache.svg" alt="On the left, the query of on, (0.030, 2.000), labeled computed, used once, not stored. Arrows lead from it to four cached keys: (1.000, 0.000) for the, (1.540, 1.010) for cat, (-0.416, 1.020) for sat and (-1.990, 0.030) for on. Next to them are the four cached values. The row for on, in both the keys and the values, is drawn faintly and labeled added by this run.">
Decoding "on" in head 1 of the running example. Its key and value join the cache, and its query is compared with every cached key.
</Figure>

#### Cache size

The cache holds a key and a value per token, per key-value head, per layer:

$$
\text{numbers stored} = 2 \times \text{layers} \times \text{key-value heads} \times \text{head size} \times \text{tokens}.
$$

For GPT-2 small at 1,024 tokens that is 2 × 12 × 12 × 64 × 1,024 = 18,874,368 numbers. At 2 bytes per number it comes to about 38 MB per conversation.

For a 70-billion-weight model such as Llama 2 70B, with 80 layers, 64 query heads and 8 key-value heads of 128 numbers, a 4,096-token conversation needs 2 × 80 × 8 × 128 × 4,096 = 671,088,640 numbers, which is 1.25 GiB. So 256 conversations need 320 GiB on top of 140 GB of weights. When many conversations are served at once, the cache, not the weights, is what runs out.

#### Decoding speed

**Operations per byte.** Decoding "on" in head 1 reads the 4 cached keys and the 4 cached values, 16 numbers or 32 bytes at 2 bytes each. It uses them in 16 multiply-adds, 8 for the scores and 8 for the weighted sum, which is 32 operations when each multiply and each add counts as one. Operations per byte read, the **arithmetic intensity**, is then

$$
\frac{\text{operations}}{\text{bytes read}} = \frac{32}{32} = 1.
$$

The ratio stays 1 at any length and any head size, because every cached number is used in exactly one multiply-add.

**Waiting on memory.** An A100 does about 312 trillion operations a second but reads only about 2 trillion bytes, so it can do about 156 operations in the time it reads one byte. At 1 operation per byte, attention during decode uses about 1 ÷ 156 = 0.6% of that arithmetic, and its time goes into reading the cache: decode is **memory-bound**. So the attention part of decoding is set by how much cache is read: halve the cache and the attention part of each token takes roughly half as long. A prefill uses each key it reads for every later query of the prompt, up to 100 times in a 100-token prompt, so it is limited by arithmetic instead: it is **compute-bound**.

#### A chunk of new tokens

**The shifted mask.** Sometimes several new tokens arrive in one run, for example a follow-up message added to a conversation whose cache already exists. The new tokens come after the cached ones, so the causal mask has to be shifted by the number of cached tokens. With "the cat sat" in the cache and the chunk "on the" arriving, "on" may see 4 keys and the second "the" all 5.

<Figure src="assets/module-media/efficient-chunk-mask.svg" alt="Two tables of head 1 scores for the chunk on the, with rows on and the and columns the, cat, sat, on and the. Shifted by the 3 cached tokens, the row of on shows 0.021, 1.461, 1.434 and 0.000, and the row of the shows all five scores. Not shifted, the row of on shows only 0.021, its score for the first token, and the row of the shows only 0.028 and 0.757.">
Head 1 scores of the chunk "on the" after "the cat sat" was cached. Blank cells are hidden by the mask.
</Figure>

**The unshifted mask.** A mask built as if the chunk started at position 1 lets "on" see 1 key and the second "the" 2. Nothing fails, since the output has the right shape, but in head 1 "on" puts all its weight on "the" and returns the value of "the", (1.000, 1.000), instead of (0.722, 0.373). PyTorch's `scaled_dot_product_attention` builds this unshifted mask when it is given `is_causal=True` and fewer queries than keys. With a cache, the shifted mask is passed instead, and a single new token needs no mask at all, since it may see every cached key.

### Running example

#### What is kept

After the prefill of "the cat sat", the cache of the one-layer model holds:

| Token | Key, head 1 | Key, head 2 | Value, head 1 | Value, head 2 |
|---|---|---|---|---|
| the | (1.000, 0.000) | (1.000, 1.000) | (1.000, 1.000) | (0.000, 1.000) |
| cat | (1.540, 1.010) | (1.540, 1.000) | (0.841, 1.540) | (1.010, 1.000) |
| sat | (−0.416, 1.020) | (−0.416, 2.000) | (0.909, −0.416) | (1.020, 2.000) |

That is 2 × 1 × 2 × 2 × 3 = 24 numbers, by the formula above: a key and a value, 1 layer, 2 heads of 2 numbers, 3 tokens.

#### Decoding one token

To decode "on", the model adds its key and value as a fourth row and compares its head 1 query, (0.030, 2.000), with the four keys:

| Key of | Key | Dot product with (0.030, 2.000) | Divided by 1.414 | Weight |
|---|---|---|---|---|
| the | (1.000, 0.000) | 0.030 | 0.021 | 0.097 |
| cat | (1.540, 1.010) | 2.066 | 1.461 | 0.409 |
| sat | (−0.416, 1.020) | 2.028 | 1.434 | 0.398 |
| on | (−1.990, 0.030) | 0.000 | 0.000 | 0.095 |

Only this row is computed. The rest of the block runs for the one new token. The cache changes how much work is done, not what the model predicts.

```python
import numpy as np

# Cache after the prefill: one row per token (head 1 keys and values).
K_cache = [np.array([1.000, 0.000]), np.array([1.540, 1.010]),
           np.array([-0.416, 1.020])]
V_cache = [np.array([1.000, 1.000]), np.array([0.841, 1.540]),
           np.array([0.909, -0.416])]

# Decode "on": compute only its own query, key and value.
q, k, v = np.array([0.030, 2.000]), np.array([-1.990, 0.030]), np.array([-0.859, -1.990])
K_cache.append(k)
V_cache.append(v)

scores = np.array(K_cache) @ q / np.sqrt(2)
weights = np.exp(scores) / np.exp(scores).sum()
output = weights @ np.array(V_cache)
print(weights.round(3))      # 0.097, 0.409, 0.398, 0.095
```

### Common questions

**Why are queries not cached?** A query is used once, by its own token, to score the keys. No later token ever needs it. Keys and values are different: every later token compares against the key of "the" and may take its value.

**Does the cache change the output?** No. It stores exactly the numbers that would have been recomputed, so the prediction is identical. Only the amount of work changes.

**Can two conversations share a cache?** Only for a prefix they have in common. Keys and values depend on every token before them, so the cache of one text is useless for a different one. A shared system prompt at the start can be cached once and reused.

**Is the cache used in training?** No. In training the whole text is present and processed in one run, like a prefill, so there is nothing to keep between runs.

The next section, [Sharing keys and values](#lesson-sharing-keys-and-values), makes the cache smaller.

## Sharing keys and values

### The problem

The cache above stores a key and a value for every head, so its size grows with the number of heads.

For example, the running example has 2 heads of 2 numbers, so it stores 2 keys and 2 values, 8 numbers, for every token. Llama 2 70B has 64 heads of 128 numbers, so each token costs 64 × (128 + 128) = 16,384 numbers in every one of its 80 layers.

<Figure src="assets/module-media/efficient-problem-sharing.svg" alt="An 8 by 8 grid of 64 small squares, labeled one token, one layer: 64 heads. One square is shaded, and a note says one square is one head's key and value, 128 + 128 = 256 numbers. The total is 64 times 256 = 16,384 numbers, for every token, in each of 80 layers.">
What Llama 2 70B stores for one token in one layer.
</Figure>

The heads cannot simply be removed. They are what lets a token look for several things at once, as in [Multi-head](2.37-TF17-transformer-weighted-sum.md#lesson-multi-head) in Build a Transformer. Making the cache smaller means storing fewer keys and values without losing too much of what the heads do.

### Earlier approaches

In standard multi-head attention, every head stores its own keys and values. That lets each head find and receive something different, and it is why the cache is so large: Llama 2 70B would store 64 keys and 64 values for every token in each of its 80 layers.

### Sharing

**The idea.** Each head's query is used once and never stored. So heads can keep their own queries, and still look for different things, while sharing the keys and values that are stored.

<Figure src="assets/module-media/efficient-sharing.svg" alt="Three panels, each with four query boxes q1 to q4 on top and boxes of stored keys and values below. In multi-head attention each query points to its own K, V box: 4 sets stored. In grouped-query attention with 2 groups, q1 and q2 share one box and q3 and q4 share another: 2 sets stored. In multi-query attention all four queries point to a single box: 1 set stored.">
Four heads under three schemes. Every head keeps its own query. What changes is how many sets of keys and values are stored.
</Figure>

**Multi-query attention** (MQA, Shazeer, 2019). All heads share one set. With 64 heads the cache shrinks 64 times, but quality drops.

**Grouped-query attention** (GQA, Ainslie et al., 2023). Groups of heads share a set. Llama 2 70B uses 8 groups of 8 heads, which shrinks the cache 64 ÷ 8 = 8 times with little loss in quality.

**Which set a head reads.** Heads are grouped in order. In the grouped-query panel above, q1 and q2 share the first set and q3 and q4 the second. Code that stores 2 sets and lines them up with 4 heads must copy each set twice in a row, set 1, set 1, set 2, set 2 (`np.repeat`). Copying the whole list twice, set 1, set 2, set 1, set 2 (`np.tile`), gives q2 and q3 the wrong set without any error. In Llama 2 70B, head 13 is in the second group of 8 and reads set 2, where the second way of copying would give it set 5. PyTorch's `scaled_dot_product_attention` with `enable_gqa=True` makes the first, correct copy itself.

**Converting a model.** A model trained with multi-head attention can be converted to grouped-query attention without training it again from the start (Ainslie et al., 2023). The key weights of the heads in a group are averaged into one shared set of key weights, the value weights likewise, and the model is then trained a little further, about 5% of its original training. In the running example, head 1's key is the second and third numbers of a token's vector and head 2's key the second and fourth. So the averaged key of "cat", whose vector is (0.841, 1.540, 1.010, 1.000), is (1.540, (1.010 + 1.000) ÷ 2) = (1.540, 1.005). Before the further training, the outputs for "sat" are:

| Keys and values used | Head 1 | Head 2 |
|---|---|---|
| Each head its own | (0.872, 1.135) | (0.893, 1.771) |
| Head 1's for both, as in the running example below | (0.872, 1.135) | (0.896, 0.347) |
| The average of both heads | (0.859, 1.091) | (0.906, 0.907) |

Averaging spreads the change over both heads: head 1 moves a little, and head 2 moves less than with head 1's set alone. Ainslie et al. found averaging a better start for the further training than keeping one head's weights.

**Multi-head latent attention** (MLA, DeepSeek-V2, 2024). Every head is kept, but each token's keys and values are stored as a short compressed summary, about the size of 2 or 3 shared sets instead of 64.

**The saving.** The cache size is in proportion to the number of sets stored. For Llama 2 70B with 4,096 tokens:

| Method | Sets of keys and values stored | Cache per conversation |
|---|---|---|
| Multi-head attention | 64 | 10 GiB |
| Grouped-query attention, 8 groups | 8 | 10 GiB ÷ 8 = 1.25 GiB |
| Multi-query attention | 1 | 10 GiB ÷ 64 = 160 MiB |
| Multi-head latent attention | A compressed summary, the size of about 2.25 sets | About 360 MiB |

The saving multiplies with the number of conversations served at once: 32 conversations need 32 × 10 GiB = 320 GiB of cache with multi-head attention and 32 × 1.25 GiB = 40 GiB with grouped-query attention.

#### Multi-head latent attention

**One short vector.** Every head's key and value is computed from the same token vector by fixed weights. So it is enough to store one short vector per token, the **latent**, and rebuild each head's key and value from it. In the running example the token's own 4 numbers can serve as the latent: for "cat", (0.841, 1.540, 1.010, 1.000) gives head 1's key (1.540, 1.010) and value (0.841, 1.540), and head 2's key (1.540, 1.000) and value (1.010, 1.000). Storing 4 numbers per token instead of 8 halves the cache, as one shared set does, but every head keeps its own keys and values: head 2's output for "sat" stays (0.893, 1.771).

<Figure src="assets/module-media/efficient-latent.svg" alt="The latent of cat, four stored numbers 0.841, 1.540, 1.010 and 1.000. Arrows lead from it to four faint pairs: head 1 key 1.540 and 1.010, head 1 value 0.841 and 1.540, head 2 key 1.540 and 1.000, head 2 value 1.010 and 1.000. A note says they are rebuilt from the latent when needed, not stored.">
What multi-head latent attention stores for "cat" in the running example: 4 numbers, from which both heads' keys and values follow.
</Figure>

**No rebuilding.** The keys never actually have to be rebuilt. A head's key weights can be applied to its query instead, once, and the result compared with the stored latents directly. Head 1 reads the second and third numbers of a latent, so its query for "on", (0.030, 2.000), becomes (0.000, 0.030, 2.000, 0.000), and against the latent of "cat" it gives 0.030 × 1.540 + 2.000 × 1.010 = 2.066, the same dot product as in the [KV cache](#lesson-kv-cache) section. The value weights move into the output weights in the same way.

**Position.** Models with rotary positions ([RoPE](3.7-TF6-relative-position-rope-positional-methods.md)) turn each key by an angle that depends on the key's position. The turn would sit between the latent and the score, so the key weights could no longer be moved onto the query once for all keys. MLA therefore keeps a small separate key, 64 numbers in DeepSeek-V2, that carries the position, is shared by all heads and is stored next to the latent.

<ProblemCard id="eff-two-schemes-four-numbers" />

**Real sizes.** Real models compute the latent from the token vector with weights of its own, so it can be much shorter than the vector: 512 numbers in DeepSeek-V2, whose token vectors have 5,120. With the position key that is 512 + 64 = 576 numbers per token in each layer, against 2 × 128 × 128 = 32,768 if its 128 heads stored keys and values of their own, about 57 times fewer. 576 numbers are as many as 576 ÷ 256 = 2.25 shared sets of 128 + 128 numbers, the 2.25 in the table above, and DeepSeek reported quality above that of full multi-head attention in their tests.

### Running example

#### One shared set

The running example's 2 heads store 8 numbers per token. With multi-query attention both share head 1's keys and values, which halves that. Head 2 keeps its own query, (−0.416, 2.000) for "sat":

| Key of | Shared key | Dot product with (−0.416, 2.000) | Divided by 1.414 | Weight |
|---|---|---|---|---|
| the | (1.000, 0.000) | −0.416 | −0.294 | 0.091 |
| cat | (1.540, 1.010) | 1.379 | 0.975 | 0.324 |
| sat | (−0.416, 1.020) | 2.213 | 1.565 | 0.585 |

#### The cost

Head 2 still looks mostly at "sat", but it now receives head 1's values, so its output is (0.896, 0.347) instead of (0.893, 1.771). Shared heads can look in different places but bring back the same kind of information, which is the quality cost grouped-query attention reduces.

```python
import numpy as np

q2 = np.array([-0.416, 2.000])                       # head 2's own query for "sat"
K1 = np.array([[1.000, 0.000], [1.540, 1.010], [-0.416, 1.020]])   # shared keys
V1 = np.array([[1.000, 1.000], [0.841, 1.540], [0.909, -0.416]])   # shared values

scores = K1 @ q2 / np.sqrt(2)
weights = np.exp(scores) / np.exp(scores).sum()
print(weights.round(3), (weights @ V1).round(3))     # about [0.091 0.324 0.585] [0.895 0.347]; the inputs above are rounded, and the unrounded example gives (0.896, 0.347)
```

### Common questions

**Why share keys and values but not queries?** Only keys and values are stored. Queries are computed, used once and thrown away, so sharing them would save no memory and would make every head look at the same tokens.

**Why did head 2's output change?** Its weights still favor "sat" (0.585), but the values it averages are now head 1's. So it returns (0.896, 0.347) where its own values gave (0.893, 1.771). The head can choose where to look, but not what it receives.

**Does sharing make the model smaller too?** A little. With fewer sets there are fewer key and value weights. The main saving is in the cache, which is per conversation and grows with every token, while the weights are stored once.

**How is the number of groups chosen?** It is a trade between memory and quality. 1 group is multi-query attention, and as many groups as heads is ordinary multi-head attention. Llama 2 70B uses 8 groups for its 64 heads.
