# 4.9 · TF27 · 2. KV cache

> **Goal:** Keeping keys and values, cache size and memory-bound decoding.
> **Stage:** Advanced, Extension topics.

## Prerequisites

- [1. Prefill and decode](4.8-TF26-efficient-prefill-and-decode.md)

## The problem

Step 1 showed that the keys and values of earlier tokens never change. So they can be computed once and kept. Keeping them costs memory, and the amount adds up.

There is a key and a value for every token, in every key-value head, in every layer, and a separate set for every conversation the model is serving. For example, in Llama 2 70B one token costs 320 KiB of cache. A 4,096-token conversation needs 1.25 GiB, and 256 conversations at once need 320 GiB, more than twice the 140 GB of the model's weights.

<Figure src="assets/module-media/efficient-problem-cache.svg" alt="A plot of cache size in GiB against the number of tokens in one conversation with Llama 2 70B. The line rises steadily, by 320 KiB for every token, and reaches 1.25 GiB at 4,096 tokens.">
The cache of one conversation grows with every token.
</Figure>

So the questions are what exactly has to be kept, and how much it costs to keep it.

## Earlier approaches

### Recompute everything

This is the waste measured in Step 1: 333,833,500 scores per head for a 1,000-token reply instead of 500,500, so 333,333,000 of them are thrown away.

### Keep everything

Keeping every number computed for earlier tokens would also avoid recomputation, but their queries, scores and weights are never used again. Later tokens need the key of "the", (1.000, 0.000) in head 1, but never its query.

## The KV cache

**What is kept.** The **KV cache** keeps only the keys and values of earlier tokens. Each decode run computes the new token's query, key and value, adds the key and value to the cache, and compares the query with every cached key. For example, after "the cat sat" the cache holds 3 keys and 3 values per head, and decoding "on" adds a fourth of each.

<Figure src="assets/module-media/efficient-kv-cache.svg" alt="On the left, the query of on, (0.030, 2.000), labeled computed, used once, not stored. Arrows lead from it to four cached keys: (1.000, 0.000) for the, (1.540, 1.010) for cat, (-0.416, 1.020) for sat and (-1.990, 0.030) for on. Next to them are the four cached values. The row for on, in both the keys and the values, is drawn faintly and labeled added by this run.">
Decoding "on" in head 1 of the running example. Its key and value join the cache, and its query is compared with every cached key.
</Figure>

### Cache size

The cache holds a key and a value per token, per key-value head, per layer:

$$
\text{numbers stored} = 2 \times \text{layers} \times \text{key-value heads} \times \text{head size} \times \text{tokens}.
$$

For GPT-2 small at 1,024 tokens that is 2 × 12 × 12 × 64 × 1,024 = 18,874,368 numbers. At 2 bytes per number it comes to about 38 MB per conversation.

For a 70-billion-weight model such as Llama 2 70B, with 80 layers, 64 query heads and 8 key-value heads of 128 numbers, a 4,096-token conversation needs 2 × 80 × 8 × 128 × 4,096 = 671,088,640 numbers, which is 1.25 GiB. So 256 conversations need 320 GiB on top of 140 GB of weights. When many conversations are served at once, the cache, not the weights, is what runs out.

### Decoding speed

**Operations per byte.** Decoding "on" in head 1 reads the 4 cached keys and the 4 cached values, 16 numbers or 32 bytes at 2 bytes each. It uses them in 16 multiply-adds, 8 for the scores and 8 for the weighted sum, which is 32 operations when each multiply and each add counts as one. Operations per byte read, the **arithmetic intensity**, is then

$$
\frac{\text{operations}}{\text{bytes read}} = \frac{32}{32} = 1.
$$

The ratio stays 1 at any length and any head size, because every cached number is used in exactly one multiply-add.

**Waiting on memory.** An A100 does about 312 trillion operations a second but reads only about 2 trillion bytes, so it can do about 156 operations in the time it reads one byte. At 1 operation per byte, attention during decode uses about 1 ÷ 156 = 0.6% of that arithmetic, and its time goes into reading the cache: decode is **memory-bound**. So the attention part of decoding is set by how much cache is read: halve the cache and the attention part of each token takes roughly half as long. A prefill uses each key it reads for every later query of the prompt, up to 100 times in a 100-token prompt, so it is limited by arithmetic instead: it is **compute-bound**.

### A chunk of new tokens

**The shifted mask.** Sometimes several new tokens arrive in one run, for example a follow-up message added to a conversation whose cache already exists. The new tokens come after the cached ones, so the causal mask has to be shifted by the number of cached tokens. With "the cat sat" in the cache and the chunk "on the" arriving, "on" may see 4 keys and the second "the" all 5.

<Figure src="assets/module-media/efficient-chunk-mask.svg" alt="Two tables of head 1 scores for the chunk on the, with rows on and the and columns the, cat, sat, on and the. Shifted by the 3 cached tokens, the row of on shows 0.021, 1.461, 1.434 and 0.000, and the row of the shows all five scores. Not shifted, the row of on shows only 0.021, its score for the first token, and the row of the shows only 0.028 and 0.757.">
Head 1 scores of the chunk "on the" after "the cat sat" was cached. Blank cells are hidden by the mask.
</Figure>

**The unshifted mask.** A mask built as if the chunk started at position 1 lets "on" see 1 key and the second "the" 2. Nothing fails, since the output has the right shape, but in head 1 "on" puts all its weight on "the" and returns the value of "the", (1.000, 1.000), instead of (0.722, 0.373). PyTorch's `scaled_dot_product_attention` builds this unshifted mask when it is given `is_causal=True` and fewer queries than keys. With a cache, the shifted mask is passed instead, and a single new token needs no mask at all, since it may see every cached key.

## Running example

### What is kept

After the prefill of "the cat sat", the cache of the one-layer model holds:

| Token | Key, head 1 | Key, head 2 | Value, head 1 | Value, head 2 |
|---|---|---|---|---|
| the | (1.000, 0.000) | (1.000, 1.000) | (1.000, 1.000) | (0.000, 1.000) |
| cat | (1.540, 1.010) | (1.540, 1.000) | (0.841, 1.540) | (1.010, 1.000) |
| sat | (−0.416, 1.020) | (−0.416, 2.000) | (0.909, −0.416) | (1.020, 2.000) |

That is 2 × 1 × 2 × 2 × 3 = 24 numbers, by the formula above: a key and a value, 1 layer, 2 heads of 2 numbers, 3 tokens.

### Decoding one token

To decode "on", the model adds its key and value as a fourth row and compares its head 1 query, (0.030, 2.000), with the four keys:

| Key of | Key | Dot product with (0.030, 2.000) | Divided by 1.414 | Weight |
|---|---|---|---|---|
| the | (1.000, 0.000) | 0.030 | 0.021 | 0.097 |
| cat | (1.540, 1.010) | 2.066 | 1.461 | 0.409 |
| sat | (−0.416, 1.020) | 2.028 | 1.434 | 0.398 |
| on | (−1.990, 0.030) | 0.000 | 0.000 | 0.095 |

Only this row is computed. The rest of the block runs for the one new token. The cache changes how much work is done, not what the model predicts.

```python
import numpy as np

# Cache after the prefill: one row per token (head 1 keys and values).
K_cache = [np.array([1.000, 0.000]), np.array([1.540, 1.010]),
           np.array([-0.416, 1.020])]
V_cache = [np.array([1.000, 1.000]), np.array([0.841, 1.540]),
           np.array([0.909, -0.416])]

# Decode "on": compute only its own query, key and value.
q, k, v = np.array([0.030, 2.000]), np.array([-1.990, 0.030]), np.array([-0.859, -1.990])
K_cache.append(k)
V_cache.append(v)

scores = np.array(K_cache) @ q / np.sqrt(2)
weights = np.exp(scores) / np.exp(scores).sum()
output = weights @ np.array(V_cache)
print(weights.round(3))      # 0.097, 0.409, 0.398, 0.095
```

## Common questions

**Why are queries not cached?** A query is used once, by its own token, to score the keys. No later token ever needs it. Keys and values are different: every later token compares against the key of "the" and may take its value.

**Does the cache change the output?** No. It stores exactly the numbers that would have been recomputed, so the prediction is identical. Only the amount of work changes.

**Can two conversations share a cache?** Only for a prefix they have in common. Keys and values depend on every token before them, so the cache of one text is useless for a different one. A shared system prompt at the start can be cached once and reused.

**Is the cache used in training?** No. In training the whole text is present and processed in one run, like a prefill, so there is nothing to keep between runs.
