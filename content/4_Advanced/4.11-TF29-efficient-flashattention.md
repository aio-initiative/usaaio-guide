## FlashAttention

### The problem

When a long text is read, each head builds a table with a score for every pair of tokens. At 8,192 tokens that is 8,192 × 8,192 = 67 million scores, which at 2 bytes each is 128 MiB per head.

A GPU has a small amount of fast on-chip memory (SRAM) next to its processors, roughly 20 MB, and a large amount of slower main GPU memory (HBM). The table does not fit in the fast part.

<Figure src="assets/module-media/efficient-problem-flash.svg" alt="Two squares drawn to scale by area. The large one is the table of scores for one head at 8,192 tokens, 128 MiB. The small shaded one in its corner is the fast memory, about 20 MB. Beside them, four steps: write the scores, read them back, write the weights, read them back. A note says every trip is to slow main memory.">
The table of scores is several times larger than the fast memory, so it has to live in slow memory.
</Figure>

So the usual method makes four trips to slow memory. It writes the scores, reads them back for the softmax, writes the weights, and reads them back to combine the values. The arithmetic is quick. The memory traffic is what takes the time: [Part 1](4.7-TF25-efficient-setup.md#lesson-setup) gave the figure of 156 operations in the time it takes to read one byte.

### Earlier approaches

#### Doing it in one pass

Doing everything at once in fast memory seemed impossible, because the softmax divides by the total of a whole row, and a long row does not fit. To turn the scores of "sat", 0.721, 2.539 and 1.142, into weights, you seem to need the total of the whole row, 17.857, before any weight is known. ([Mask and softmax](2.34-TF14-transformer-qkv.md#lesson-mask-and-softmax) in Build a Transformer prints 17.856 for this row: it adds its powers after rounding each to three decimals, and their full-precision sum is 17.857.)

#### Approximate attention

Computing only some of the scores, for example scoring each token only against its 256 nearest neighbors, reduced the arithmetic and changed the result, but often did not run faster in practice, because the memory traffic stayed the same (Dao et al., 2022).

### FlashAttention

**The idea.** **FlashAttention** computes exactly the same attention without ever storing the full table. The keys and values are processed in blocks that fit in fast memory. For each query it keeps three running numbers: the largest score so far, a running total for the softmax, and a running weighted sum of values.

<Figure src="assets/module-media/efficient-flash.svg" alt="Three boxes joined by arrows. Block 1, the: largest 0.721, total 1.000, sum (1.000, 1.000). An arrow labeled shrink by 0.162 leads to block 2, cat and sat: largest 2.539, total 1.409, sum (1.228, 1.599). A last arrow leads to divide sum by total: output for sat, (0.872, 1.135). A note says: three running numbers per query, and the full row of scores is never stored.">
The row of "sat" in head 1, processed in two blocks of keys.
</Figure>

**The running total.** The softmax weight of a score $s$ can be written with any reference score $m$ subtracted from every score, because the factor cancels:

$$
\frac{e^{s_i}}{e^{s_1} + e^{s_2} + \dots} = \frac{e^{s_i - m}}{e^{s_1 - m} + e^{s_2 - m} + \dots}.
$$

FlashAttention uses the largest score seen so far as $m$, which keeps every term at 1 or below. For example, with the scores 0.721 and 2.539, $m = 2.539$ gives the terms $e^{-1.818} = 0.162$ and $e^{0} = 1$.

**When a larger score arrives.** The totals so far were computed with the old $m$. Multiplying them by $e^{m_\text{old} - m_\text{new}}$ converts them to the new one. A new largest score of 2.539, after 0.721, shrinks them by $e^{0.721 - 2.539} = 0.162$.

**The result.** At the end, the weighted sum is divided by the total. Nothing is approximated, memory grows only with the length, and attention runs several times faster. Blocks of keys that lie entirely in the future, under the causal mask, are skipped.

**Training.** The backward pass of training needs every weight again, to work out how each score should change. FlashAttention does not store the weights. It keeps two numbers per query, the largest score and the total, and recomputes the scores from the queries and keys during the backward pass. For "sat" the two numbers are 2.539 and 1.409, and they give back each weight. The weight of "the" is $e^{0.721 - 2.539} \div 1.409 = 0.162 \div 1.409 = 0.115$, and that of "sat" is $e^{1.142 - 2.539} \div 1.409 = 0.247 \div 1.409 = 0.175$, the same as the ordinary softmax gives. For 8,192 tokens that is 16,384 numbers per head instead of 67 million weights. Every score is computed twice, and the backward pass still runs faster, because memory traffic is what sets its speed.

#### Sliding windows

**Skipped blocks.** In **sliding-window attention** each token looks only at the last $w$ tokens, itself included. FlashAttention's loop then skips every block of keys that lies entirely before the window, as it skips blocks in the future, so each token costs the same work however long the text is. Scoring only nearby tokens did not run faster on its own (see Earlier approaches), but here the skipped blocks are never read from slow memory at all. With a window of 2, "sat" looks at "cat" and itself, so block 1, which holds only "the", is skipped. The loop starts at block 2 with largest score 2.539, total $1.000 + 0.247 = 1.247$ and weighted sum (0.841, 1.540) + 0.247 × (0.909, −0.416) = (1.066, 1.437). The output is (1.066 ÷ 1.247, 1.437 ÷ 1.247) = (0.855, 1.152) instead of (0.872, 1.135): unlike FlashAttention itself, a window changes the result.

<Figure src="assets/module-media/efficient-window.svg" alt="On the left, head 1 scores for the cat sat on with a window of 2: each row keeps only its own score and the one before it, 0.000 for the, 0.714 and 1.814 for cat, 2.539 and 1.142 for sat, 1.433 and 0.000 for on. Every other cell is blank. On the right, a cache of two slots after each token: the, then the and cat, then sat and cat, then sat and on.">
A window of 2 in head 1. Each token scores only itself and the token before it, so the cache needs only 2 slots, and each new token overwrites the oldest.
</Figure>

**A rolling cache.** A key or value older than the window is never read again, so the cache needs only $w$ slots. Token number $i$, counting from 0, goes into slot $i \bmod w$, over the token $w$ places before it. With $w = 2$, "the" goes into slot 0 and "cat" into slot 1, then "sat" overwrites "the" and "on" overwrites "cat". The cache stays at $w$ tokens however long the text gets.

**Reach.** A token still learns about tokens further back, through the layers. With a window of 2, "cat" reads "the" in the first layer, and "sat" reads that output of "cat" in the second. So each layer reaches $w - 1$ positions further back, 2 × (2 − 1) = 2 positions after 2 layers. Mistral 7B, with a window of 4,096 in each of its 32 layers, has a theoretical reach of 32 × 4,095 = 131,040 positions, though its 8,192-token context is the real limit. Gemma 2 instead alternates windowed layers with layers of full attention, so that every other layer reads the whole text at once.

### Running example

#### Two blocks

Take the row of "sat" in head 1, with scores 0.721, 2.539 and 1.142, and let the keys arrive in two blocks: first "the", then "cat" and "sat".

| Stage | Largest score | Running total | Running weighted sum |
|---|---|---|---|
| Block 1: "the" | 0.721 | $e^{0} = 1.000$ | 1.000 × (1.000, 1.000) = (1.000, 1.000) |
| Block 2 has a larger score, 2.539: shrink by $e^{0.721 - 2.539} = 0.162$ | 2.539 | 0.162 | (0.162, 0.162) |
| Add "cat": $e^{2.539 - 2.539} = 1.000$ | 2.539 | 1.162 | + 1.000 × (0.841, 1.540) = (1.003, 1.702) |
| Add "sat": $e^{1.142 - 2.539} = 0.247$ | 2.539 | 1.409 | + 0.247 × (0.909, −0.416) = (1.228, 1.599) |

#### The result

Dividing gives (1.228 ÷ 1.409, 1.599 ÷ 1.409) = (0.872, 1.135), exactly head 1's output for "sat" in [Weighted sum](2.37-TF17-transformer-weighted-sum.md#lesson-weighted-sum) of Build a Transformer, without ever storing the full row of weights.

```python
import numpy as np

scores = np.array([0.721, 2.539, 1.142])
values = np.array([[1.000, 1.000], [0.841, 1.540], [0.909, -0.416]])
blocks = [[0], [1, 2]]                     # "the", then "cat" and "sat"

largest, total, weighted = -np.inf, 0.0, np.zeros(2)
for block in blocks:
    new_largest = max(largest, scores[block].max())
    shrink = np.exp(largest - new_largest)   # rescale what came before
    p = np.exp(scores[block] - new_largest)
    total = total * shrink + p.sum()
    weighted = weighted * shrink + p @ values[block]
    largest = new_largest

print((weighted / total).round(3))           # about [0.871 1.135]; the inputs are rounded, so the last digit differs from Build a Transformer's (0.872, 1.135)
```

### Common questions

**Is FlashAttention an approximation?** No. It gives the same output as ordinary attention, up to rounding. The running example ends at (0.872, 1.135), the output of [Weighted sum](2.37-TF17-transformer-weighted-sum.md#lesson-weighted-sum) in Build a Transformer.

**Does it compute fewer scores?** No. Every score is still computed. What it avoids is writing the table of scores to slow memory and reading it back, which is where the time went.

**Why subtract the largest score?** To keep the numbers small. $e^{12}$ is 162,755, already more than the 65,504 that an IEEE fp16 number can hold (bfloat16, also 16 bits, reaches about 3.4 × 10^38). With the largest score subtracted, every term is $e$ to a power of 0 or less, so it lies between 0 and 1.

**Does the block size change the answer?** No. One block of three keys, three blocks of one, or the two blocks used here all end at the same output. The block size is chosen to fit the fast memory.

The next section, [Linear attention](#lesson-linear-attention), changes the calculation itself so that its cost grows only with the length.

## Linear attention

### The problem

The KV cache (part 2) and FlashAttention (above) make attention cheaper without changing what it computes. Sharing keys and values (part 2) and sliding windows (above) save more by changing the result. With attention kept exact, two costs remain, and both grow with the length of the text:

- **Work per token.** Every new token is compared with every earlier one. At 1,000 tokens that is 1,000 comparisons for the next token. At 100,000 it is 100,000.
- **Memory.** The cache holds a key and a value for every earlier token, so it grows with every token generated.

<Figure src="assets/module-media/efficient-problem-linear.svg" alt="A plot of the number of keys compared for the next token against the number of tokens so far, both in thousands. For softmax attention the line rises steadily, one comparison per earlier token, reaching 100,000 at 100,000 tokens. A dashed flat line near the bottom marks the goal: the same work for every token.">
With softmax attention, each new token costs more than the one before.
</Figure>

The goal here is attention whose work per token stays the same however long the text is, and whose memory stays fixed during generation.

### Earlier approaches

#### Recurrent networks

They have fixed memory and constant cost per token, but read one token at a time and forget over distance (see [Setup](2.30-TF10-transformer-setup.md#lesson-setup) in Build a Transformer): by the blank in "The students who failed the exam ___", "students" may already be lost.

#### Faster softmax attention

The KV cache and FlashAttention keep attention exact, and shared keys and values trade some of the result for a smaller cache. All three still do work that grows with the square of the length: FlashAttention still computes about 67 million scores per head for 8,192 tokens. A sliding window (see [FlashAttention](#lesson-flashattention)) fixes the work per token by changing the result, since no token can look directly further back than the window.

### Linear attention

**A simpler similarity.** The obstacle is the softmax, which forces every score to be computed separately. **Linear attention** (Katharopoulos et al., 2020) replaces it. Each query and key is passed through a function $\phi$ that makes its numbers positive, and the similarity is their dot product. For example, 1.020 becomes 2.020 and −0.416 becomes 0.660. The weights are the similarities divided by their total:

$$
\text{output} = \frac{\sum_j \big(\phi(q) \cdot \phi(k_j)\big) \, v_j}{\sum_j \phi(q) \cdot \phi(k_j)}.
$$

**The running state.** The query appears in every term, so it can be taken out of both sums:

$$
\text{output} = \frac{\phi(q) \cdot \big(\sum_j \phi(k_j) \, v_j^\top\big)}{\phi(q) \cdot \big(\sum_j \phi(k_j)\big)}.
$$

The two sums in brackets do not depend on the query. They are a small running **state** that each token adds to, and every output is read from it. Memory stays fixed however long the text gets, like a recurrent network: in the running example the state is 6 numbers, after 3 tokens or after 3,000.

**Counting the work.** For a whole text of $n$ tokens and head size $d$, softmax attention computes the $n \times n$ table of scores, each a dot product of $d$ numbers, and then as many multiply-adds again for the weighted sums, about $2 \times n \times n \times d$. Linear attention adds $n$ products of $d \times d$ numbers into the state and reads $n$ outputs from it, about $2 \times n \times d \times d$. In matrix form it is the same product bracketed the other way: softmax attention has to compute the $n \times n$ table $QK^\top$ before multiplying by $V$, while linear attention computes $\phi(K)^\top V$, which is only $d \times d$, first. The second way is cheaper as soon as the text is longer than the head size. At 8,192 tokens and GPT-2's head size of 64 it takes 67 million multiply-adds against 8.6 billion, 8,192 ÷ 64 = 128 times fewer.

**The price.** Softmax weights can put almost everything on one token. Linear weights are usually much flatter than softmax weights, so recalling one specific earlier token works poorly. In a test where one key is hidden among 512 others and searched for exactly, softmax attention returns its value almost perfectly, while linear attention returns a blur of everything. That is why most models still use softmax attention with FlashAttention.

<Figure src="assets/module-media/efficient-linear.svg" alt="A bar chart of the weights of sat on the, cat and sat under two schemes. Softmax attention gives 0.115, 0.709 and 0.175. Linear attention gives 0.275, 0.436 and 0.289, much more even.">
The weights of "sat" in head 1 of the running example. Linear attention spreads its weight more evenly than softmax attention.
</Figure>

**Forgetting.** The state adds in every token with the same weight and never lets go of any. A **decay** $\gamma$ between 0 and 1 shrinks the state before each new token is added,

$$
\text{state} \leftarrow \gamma \times \text{state} + \phi(k)\, v^\top,
$$

and the total of the keys likewise, so a token $a$ steps back counts $\gamma^a$ times its similarity. With $\gamma = 0.5$, "the", two steps back from "sat", counts 0.25 times and "cat" 0.5 times. The weights of "sat" become 0.119, 0.379 and 0.502 instead of 0.275, 0.436 and 0.289, and its output moves to (0.894, 0.494). A decay favors recent tokens and loses older ones faster. RetNet gives each head a fixed decay. Mamba (Gu and Dao, 2023) and gated linear attention compute the decay from each token, so the model learns what to keep and what to forget, much like the forget gate of an [LSTM](3.5-NL2-sequence-models-transfer-learning.md).

<Figure src="assets/module-media/efficient-decay.svg" alt="A bar chart of the weights of sat on the, cat and sat. Linear attention gives 0.275, 0.436 and 0.289. With a decay of 0.5, which multiplies the similarity of the by 0.25 and that of cat by 0.5, the weights become 0.119, 0.379 and 0.502.">
The weights of "sat" in head 1 with and without a decay of 0.5. The older a token, the more of its weight it loses.
</Figure>

#### Feature map of the softmax

**Powers of a dot product.** The softmax weight $e^{q \cdot k}$ can also be written as a dot product, but of endless lists. Its series is

$$
e^{s} = 1 + s + \frac{s^2}{2} + \frac{s^3}{6} + \dots,
$$

and every power of a dot product is itself a dot product of longer lists: $(q \cdot k)^2 = (q \otimes q) \cdot (k \otimes k)$, where $q \otimes q$ lists every product of two numbers of $q$, $(q_1 q_1, q_1 q_2, q_2 q_1, q_2 q_2)$ for a query of 2 numbers. Collecting the terms gives $e^{q \cdot k} = \psi(q) \cdot \psi(k)$, with a feature map $\psi$ of its own:

$$
\psi(q) = \Big(1,\ q,\ \frac{q \otimes q}{\sqrt{2}},\ \frac{q \otimes q \otimes q}{\sqrt{6}},\ \dots\Big).
$$

Take "sat" and "cat" in head 1, with the query and the key each divided by $2^{1/4} = 1.189$, so that their dot product already includes the division by 1.414: $q = (0.858, 1.682)$, $k = (1.295, 0.849)$ and $q \cdot k = 2.539$, the score of "sat" on "cat". Then $(q \cdot k)^2 = 2.539^2 = 6.447$, and the dot product of the two lists of 4 products gives the same 6.447.

**Cutting the list.** Stopping after degree $N$ gives a finite feature map. Its dot product is the series up to $s^N / N!$, and for head size $d$ it has $1 + d + d^2 + \dots + d^N$ numbers. For the score of "sat" on "cat", against the exact $e^{2.539} = 12.667$:

| Cut after degree | Features at head size 2 | Similarity of "sat" and "cat" |
|---|---|---|
| 1 | 3 | 3.539 |
| 2 | 7 | 6.762 |
| 4 | 31 | 11.222 |
| 8 | 511 | 12.651 |

Every cut leaves out the terms after it, so this list gives the softmax exactly only at its full, endless length. At real head sizes even an early cut is long: with head size 64, the cut after degree 2 already has 1 + 64 + 4,096 = 4,161 features.

<Figure src="assets/module-media/efficient-taylor.svg" alt="Two plots. On the left, the similarity of sat and cat against the degree of the cut, rising from 1.000 at degree 0 through 3.539 with 3 features, 11.222 with 31 features and 12.651 with 511 features towards a dashed line at the exact value, e to the 2.539, 12.667. On the right, the curve e to the s for scores from minus 4 to 2, with its cut after degree 1, the straight line 1 + s, which falls below zero for scores under minus 1, and its cut after degree 2, a parabola that never goes below 0.5.">
Left: the similarity of "sat" and "cat" as the list is cut after more degrees. Right: the exponential and its cuts after degree 1 and degree 2.
</Figure>

**Even degrees.** Linear attention divides by the total similarity, so every similarity must stay positive. A cut after an odd degree can go negative: after degree 1 the similarity is $1 + s$, which is −1 for a score of −2. A cut after an even degree cannot. After degree 2 it is $1 + s + s^2/2$, which is smallest at $s = -1$, where it is 0.5, and at $s = -2$ it is 1.

### Running example

#### A simpler similarity

Take the row of "sat" in head 1 again. Passing the query and keys through the function that makes their numbers positive:

| | Before | After |
|---|---|---|
| Query of "sat" | (1.020, 2.000) | (2.020, 3.000) |
| Key of "the" | (1.000, 0.000) | (2.000, 1.000) |
| Key of "cat" | (1.540, 1.010) | (2.540, 2.010) |
| Key of "sat" | (−0.416, 1.020) | (0.660, 2.020) |

Positive numbers get 1 added, and −0.416 becomes $e^{-0.416} = 0.660$. The similarities and weights:

| Key of | Similarity with (2.020, 3.000) | Linear weight | Softmax weight, for comparison |
|---|---|---|---|
| the | 2.020 × 2.000 + 3.000 × 1.000 = 7.040 | 0.275 | 0.115 |
| cat | 2.020 × 2.540 + 3.000 × 2.010 = 11.161 | 0.436 | 0.709 |
| sat | 2.020 × 0.660 + 3.000 × 2.020 = 7.393 | 0.289 | 0.175 |

The linear weights are much more even: "cat" gets 44% instead of 71%, and the output is (0.905, 0.827) instead of (0.872, 1.135).

#### The running state

The same output comes from the running state: four totals of key-number × value-number, plus the totals of the key numbers. Each token adds its own products to the totals (the entries are computed before the inputs are rounded, so the last digit can differ from the products of the rounded numbers above):

| After | Key 1 × value 1 | Key 1 × value 2 | Key 2 × value 1 | Key 2 × value 2 | Total of key 1 | Total of key 2 |
|---|---|---|---|---|---|---|
| the | 2.000 | 2.000 | 1.000 | 1.000 | 2.000 | 1.000 |
| cat | 4.138 | 5.913 | 2.691 | 4.096 | 4.540 | 3.010 |
| sat | 4.737 | 5.638 | 4.528 | 3.255 | 5.200 | 5.030 |

The output for "sat" combines its query with the last row:

- first number: (2.020 × 4.737 + 3.000 × 4.528) ÷ (2.020 × 5.200 + 3.000 × 5.030) = 23.153 ÷ 25.594 = 0.905,
- second number: (2.020 × 5.638 + 3.000 × 3.255) ÷ 25.594 = 21.154 ÷ 25.594 = 0.827.

That is the same (0.905, 0.827), from six stored numbers. With a thousand earlier tokens, the state would still be six numbers.

```python
import numpy as np

def positive(x):                       # 1 added above zero, e^x below zero
    return np.where(x > 0, x + 1.0, np.exp(np.minimum(x, 0)))

q = positive(np.array([1.020, 2.000]))
K = positive(np.array([[1.000, 0.000], [1.540, 1.010], [-0.416, 1.020]]))
V = np.array([[1.000, 1.000], [0.841, 1.540], [0.909, -0.416]])

state, key_total = np.zeros((2, 2)), np.zeros(2)
for k, v in zip(K, V):                 # one update per token, fixed size
    state += np.outer(k, v)
    key_total += k

print((q @ state / (q @ key_total)).round(3))   # about [0.904 0.826]; inputs are rounded
```

### Common questions

**Why can softmax attention not keep a running state?** Its weight needs $e^{q \cdot k}$. The feature map above writes it as a list computed from the query alone dotted with a list computed from the key alone, but that list gives the softmax exactly only at its full, endless length, and every cut of it is an approximation. A plain dot product $\phi(q) \cdot \phi(k)$ of short lists splits at once, which is what lets the keys be added up before any query arrives.

**Why are the linear weights so even?** The softmax turns a gap between scores into a ratio. "cat" beats "the" by 2.539 against 0.721, a gap of 1.818, which becomes $e^{1.818} = 6.2$ times the weight. The linear similarities are 11.161 against 7.040, only 1.6 times.

**Is the state really a fixed size?** Yes. It has one total for every pair of a key number and a value number, 2 × 2 = 4 here, plus one total for every key number, 2 here. That is 6 numbers per head however many tokens have been read.

**Is linear attention used in practice?** Rarely for language models, because of the loss of focus. Most models use softmax attention with a KV cache and FlashAttention.
